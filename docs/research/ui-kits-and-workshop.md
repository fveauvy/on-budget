# UI kits and component workshop

> **Status (2026-11-08).** Background research for [ticket #11](https://github.com/fveauvy/shoestring/issues/11) of the [map](https://github.com/fveauvy/shoestring/issues/6). Nothing here is adopted: the ADRs, `SPEC.md`, [`docs/factory.md`](../factory.md) and [`docs/architecture.md`](../architecture.md) win where it disagrees. It assumes the client model of the [charting decisions](https://github.com/fveauvy/shoestring/issues/7): a React web kit on Base UI and Tailwind 4, wrapped in Electron for the desktop, and a separate Expo iPhone kit.

> Research note, 2026-11-08. Versions are the newest stable release or release candidate that day, read from npm dist-tags and GitHub releases; betas, alphas, canaries and nightlies are named only to rule them out. T3 Code is read at commit [`6417151`](https://github.com/pingdotgg/t3code/tree/6417151c093e54dbba0e6c824c69d03983793b9a) (2026-11-08), impeccable at tag [`skill-v4.8.1`](https://github.com/pbakaus/impeccable/tree/skill-v4.8.1). Confidence: **H** high, **M** medium, **L** low. "Judgment" marks my assessment; "unverified" marks what no source or run confirms. Nothing was installed or run.

## Question

How are T3 Code's web and mobile UI kits built? Which component workshop should Shoestring use for its two kits: Storybook 10 (React Vite and React Native), Ladle, React Cosmos, or Expo showcase screens? Each is judged on impeccable's live mode and critique, the token pipeline (Terrazzo to Tailwind 4 variables, React Native and SwiftUI), visual regression and CI cost.

## TL;DR

1. **Web and desktop kit: Storybook 10.6.6 with `@storybook/react-vite`.** It is the only candidate that combines a maintained release on Vite 8, a docs site, an axe addon, story tests in Vitest 5 browser mode and an agent interface: the Storybook MCP addon (a preview feature) gives agents a component list, each component's props and stories, and a test runner (§4). Visual regression stays self-hosted: Vitest's `toMatchScreenshot` over portable stories, references made in CI's Playwright image. **M**
2. **iPhone kit: a dev-only catalog route inside the Expo app, as T3 Code does, not a workshop product.** T3 Code's `ComponentCatalogScreen` sits behind a dev-only deep link (`dev/components`) and renders the kit under a theme picker, with the app's real providers, navigation chrome and native controls (§3). Shoestring adds one page per component spec, deep links per variant and theme, and Maestro or agent-device captures. Those captures can embed in the web Storybook's page for the same spec, so one docs site covers both kits (judgment). Storybook for React Native 10.7.1 is the fallback, if on-device controls or its experimental MCP prove worth an extra Storybook entry in the app. **M**
3. **T3 Code has no workshop.** It has no Storybook, Ladle, Cosmos, Chromatic or screenshot assertion anywhere (§1.5). Web components get Vitest browser tests, visual fixes get before/after captures as proof, and its `mobile-showcase` is a store-screenshot pipeline (§3). Shoestring has no store listing, so that pipeline has no use here. Its seeded scenes, deep links and simulator settings carry over. **H**
4. **impeccable does not depend on the workshop: `PRODUCT.md` decides.** `live`, `generate` and the bundled `detect` are web-only. `ios`, `android` or `adaptive` turns them off, and the detector hook too, and Shoestring's `PRODUCT.md` says `adaptive` today (§5.1). With a web platform, live mode runs on any Vite page whose HTML file it can edit. The best such page is the app itself, seeded with the test household. Cosmos alone reuses the project's `index.html`. For Storybook's iframe and Ladle, injection is unverified. Critique runs on any URL, story pages included. On native it runs its design review alone. **H** on the mechanics, **M** on the fit.
5. **Tokens: Terrazzo 2.10's Tailwind plugin covers the web kit.** Its template injects each resolver permutation where you put an `@tz` rule (§6). React Native has no Terrazzo plugin. T3 Code's iPhone kit uses Uniwind 1.13, whose themes are Tailwind 4 `@variant` blocks. A second template could emit them (unverified). SwiftUI still needs the custom plugin ADR 0014 plans: `plugin-swift` 0.3.4 is experimental and handles colors only. No workshop renders SwiftUI. **M**
6. **Visual regression: self-hosted, free, deferred until a gap shows.** On the web, Vitest 5.1 `toMatchScreenshot` or Playwright `toHaveScreenshot`. On the iPhone, Maestro 2.12.1 `assertScreenshot` on catalog deep links, or React Native Harness 1.7.0 `toMatchImageSnapshot` (§7). Chromatic is out: its PR runs need a token, and `factory.md` puts secrets only in environments bound to `main` and tags. **M**
7. **CI cost is time, not money.** Standard GitHub-hosted runners are free for public repositories ([docs](https://docs.github.com/en/actions/concepts/billing-and-usage)). Storybook's build and story tests ride the existing Linux `web` job, and iPhone captures run in the `apple` job only when kit or native paths change, or on demand. Durations are unmeasured. **H** on price, **L** on durations.
8. **Ruled out.** Ladle: its latest npm release (5.1.1, 2025-11-04) bundles Vite 6, the Vite 8 move on `main` is unreleased, and it takes no third-party addons and offers no MCP. Storybook for React Native Web: it shows the iPhone kit through react-native-web, without UIKit, SwiftUI or SF Symbols. Expo's showcase pipeline as a workshop: it captures whole screens for stores. React Cosmos 7.4.1 is the runner-up for the web kit: lean, on the project's own Vite config and `index.html`, with a fixtures API for screenshots, but no docs pages, axe addon or MCP. **M**

## 1. T3 Code's web kit

### 1.1 Components: `components/ui` on Base UI and Tailwind 4

- **A shadcn project on the Base UI base.** [`components.json`](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/apps/web/components.json) sets style `base-mira`, CSS variables in `src/index.css`, base color zinc, `iconLibrary: lucide` and two extra registries, `@coss` (`coss.com/ui`) and `@spell` (`spell.sh`). In shadcn's registry, `base` is the Base UI base (dependency `@base-ui/react`), next to `radix` and `aria` ([bases.ts](https://github.com/shadcn-ui/ui/blob/main/apps/v4/registry/bases.ts)), and `mira` is one of eight styles ([styles.tsx](https://github.com/shadcn-ui/ui/blob/main/apps/v4/registry/styles.tsx)). The folder holds 56 files: primitives (button, menu, select, combobox, dialog, sheet, popover, tooltip, toast, number-field…) and app-level parts (sidebar, wizard, discovery-list). **H**
- **Variants.** [`button.tsx`](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/apps/web/src/components/ui/button.tsx) builds its look with `cva` from `class-variance-authority` (14 variants, 18 sizes). It renders through Base UI's `useRender` and `mergeProps`, so `render={<Link/>}` swaps the element and keeps the recipe, and it tags the element with `data-slot="button"`. **H**
- **`cn`.** [`lib/utils.ts`](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/apps/web/src/lib/utils.ts#L1-L21) runs cva's `cx` through `extendTailwindMerge`, registering the custom `text-2xs`…`text-5xs` sizes and two background images, so tailwind-merge doesn't drop them as colors. **H**
- **Ownership rule.** "`apps/web/src/components/ui` exports own their look. Pick a `variant` or `size`; do not restyle one with `className`"; a generic look becomes a new variant, a feature's look stays in the feature, and layout classes go on the parent ([AGENTS.md](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/AGENTS.md#L197)). [`web-ui.md`](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/docs/internals/web-ui.md) adds: no raw `<button>` styled as a control, Tailwind classes in the owning component, global CSS only for what classes can't express, theme rules through `@variant dark` and `@variant light`, never `.dark` selectors, and composition through exported slots (`ComposerBanner` is the reference). **H**

### 1.2 Theming and dark mode

- **Tokens are CSS variables in one file.** [`index.css`](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/apps/web/src/index.css) declares `@custom-variant dark (&:is(.dark, .dark *))` (line 5). Its `:root` holds semantic variables, the shadcn set (`--background`, `--foreground`, `--primary`, `--muted`…) plus app roles (sidebar, message, toolbar, warning, success, diff), each redefined inside a nested `@variant dark` block (lines 1113–1230). `@theme inline` maps them to Tailwind's `--color-*`, `--radius-*` and `--text-*` namespaces (line 177 on). Fonts sit in a plain `@theme` block, so Settings can override them at runtime (line 170). **H**
- **Switching.** [`useTheme.ts`](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/apps/web/src/hooks/useTheme.ts#L42) follows `(prefers-color-scheme: dark)` unless the user picks light or dark, stores the choice and syncs it to the Electron shell. Named themes set `html[data-theme-id]` and write `--app-theme-*` variables at runtime ([`themePalette.ts`](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/apps/web/src/themePalette.ts#L1533)). The palettes come from [`packages/shared/src/themePalettes.ts`](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/packages/shared/src/themePalettes.ts): 61 color roles, the default palette and five built-in themes, each with light and dark halves, plus user theme files. The server and the mobile app read the same module (§2.1). **H**
- **Contrast is a user setting.** [`appearanceContrast.ts`](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/apps/web/src/appearanceContrast.ts) writes `--appearance-contrast-*` variables that the `--contrast-*` roles mix in. `index.css` reads `forced-colors`, not `prefers-contrast`. **H**

### 1.3 Icons and the brand icon export

- **Lucide.** The web app uses `lucide-react` and `lucide` `^0.564.0` (npm `latest` is 1.70.0) and `morphicons` ([package.json](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/apps/web/package.json)). Lint routes pull-request glyphs through one `PullRequestGlyph` map (§1.4). Third-party brand marks keep their colors in `Icons.tsx` and `JetBrainsIcons.tsx`, the only files exempt from `shadcn/no-raw-colors` ([vite.config.ts](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/vite.config.ts#L540-L545)). **H**
- **Brand icons.** [`export-brand-icons.ts`](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/scripts/export-brand-icons.ts) runs Apple's Icon Composer command-line tool (`ictool`, design generation 26) on `assets/{dev,nightly,prod}/app-icon.icon`. It writes the iOS, macOS and universal 1024 px PNGs, web favicons, the Apple touch icon, PWA icons and Windows `.ico` files listed in [`brand-assets.ts`](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/scripts/lib/brand-assets.ts). The root scripts `icons:export` and `icons:check` write and verify the outputs ([package.json](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/package.json)); I found no CI step calling `icons:check`. `apply-web-brand-assets.ts` copies a channel's web icons during web and desktop builds. **H**

### 1.4 The lint rules that steer agents

`vp lint` (Vite+, Oxlint) loads two JavaScript plugins, the in-repo `oxlint-plugin-t3code` and `@shadcn/lint` 0.1.5, with `settings.shadcn.ui = "~/components/ui"` ([vite.config.ts](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/vite.config.ts#L220-L224)).

| Rule | Scope | Effect |
|---|---|---|
| `shadcn/no-unknown-classes`, `shadcn/no-raw-colors` | `apps/web/src/**` | Classes Tailwind can't generate; palette colors such as `bg-pink-500` |
| `shadcn/require-static-classes`, `shadcn/no-arbitrary-values` (with an allowlist), `shadcn/no-restyle` (`allow: ["layout"]`, a contract for `CollapsibleTrigger`) | `apps/web/src/**` outside `components/ui` | Dynamic class strings, `p-[13px]`-style values, restyling a kit export |
| `eslint/no-restricted-imports` | Web outside `components/ui` | `buttonVariants`, `toggleVariants`, `badgeVariants`, `selectTriggerVariants` ("Render the components/ui export instead of borrowing its class recipe"); lucide's git glyphs; `@pierre/diffs` `CodeView`; the `client-runtime` root |
| `eslint/no-restricted-imports` | Mobile features | `AndroidScreenHeader`, `WorkspaceAppBar` ("Use AppBar") |
| `t3code/no-mobile-uniwind-theme-escape-hatches` | `apps/mobile/src/**` | `dark:` and `light:` utilities ("do not follow registered custom themes; use an adaptive semantic token") and `useUniwindTheme` outside reviewed interop |
| React Compiler rules, `t3code/no-manual-memo`, `t3code/no-unreasoned-state-sync` | Web | `useMemo`, `useCallback`, unexplained effects; a coverage test compiles every file |

Sources: [vite.config.ts](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/vite.config.ts#L30-L79) (shared lists), [web and mobile overrides](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/vite.config.ts#L385-L420), [shadcn rules](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/vite.config.ts#L514-L590), [Uniwind rule](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/oxlint-plugin-t3code/rules/no-mobile-uniwind-theme-escape-hatches.ts), [web-ui.md](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/docs/internals/web-ui.md#react-compiler). **H**

`@shadcn/lint` is now 0.2.5 (2026-11-02). It describes itself as "an agent-first linter for Tailwind design systems". It needs Tailwind v4, not shadcn/ui, runs under ESLint or Oxlint, and its errors suggest the fix from your components, variants and theme. Its six rules: `no-restyle`, `no-raw-colors`, `no-arbitrary-values`, `no-inline-styles`, `no-unknown-classes` and `require-static-classes` ([README](https://github.com/shadcn-ui/lint#readme)). T3 Code applies it to the web only. Whether it reads Uniwind classNames is unverified. **H**

## 2. T3 Code's mobile kit

- **Stack** ([package.json](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/apps/mobile/package.json)): Expo SDK 58 (`expo` 58.0.14) and React Native 0.88.0, styled with Uniwind 1.13.0 (Tailwind 4 for React Native) plus `tailwind-merge` and `clsx`. No NativeWind or Unistyles. `components/ui` has 107 files, split by platform: `.ios.tsx`, `.android.tsx`, `.shared.tsx`, `.types.ts`. **H**
- **`@expo/ui` 58.0.20.** Android is mostly Jetpack Compose (38 import sites). iOS uses SwiftUI only for a few controls: `ProgressView`, `Slider`, `NumberField`'s picker and popover, `Chart`, a snooze sheet, and the home-screen widgets. `NativeSwitch` on iOS is React Native's `Switch`. Expo UI maps "one to one" to SwiftUI and Jetpack Compose, needs a `Host` per tree, and has a Universal set for Android, iOS and the web ([Expo UI](https://github.com/expo/expo/blob/main/docs/pages/versions/v58.0.0/sdk/ui/index.mdx)). **H**
- **Navigation.** React Navigation 7's native stack through the static API (`createNativeStackScreen`), not Expo Router ([Stack.tsx](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/apps/mobile/src/Stack.tsx)). `react-native-screens` is a patched 5.0.0 tarball that `expo install` is told to skip. SDK 58 bundles `~4.30.1` ([bundledNativeModules](https://github.com/expo/expo/blob/sdk-58/packages/expo/bundledNativeModules.json)), and 5.0.0 is still a beta on npm, so Shoestring's version rule excludes T3 Code's fork. **H**
- **Menus, blur, glass.** `@react-native-menu/menu` 2.0.0's `MenuView`, wrapped with `withUniwind` for icon colors ([Menu.tsx](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/apps/mobile/src/components/ui/Menu.tsx)). `expo-glass-effect`'s `GlassView` and `GlassContainer` where the glass API exists, and `expo-blur`'s `BlurView` as the fallback backdrop ([GlassSurface.tsx](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/apps/mobile/src/components/ui/GlassSurface.tsx), [GlassBackdrop.tsx](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/apps/mobile/src/components/ui/GlassBackdrop.tsx)). **H**
- **Icons and fonts.** SF Symbols through `expo-symbols` on iOS. Tabler icons on Android, and on iOS for a few git glyphs SF Symbols lacks. Both are wrapped with `withUniwind` ([AppSymbol.ios.tsx](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/apps/mobile/src/components/ui/AppSymbol.ios.tsx)). DM Sans, in three weights, is embedded at build time by the `expo-font` config plugin under PostScript names ([app.config.ts](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/apps/mobile/app.config.ts#L127-L131)). The type scale in `global.css` is mirrored in `typography.ts` for native style props. **H**

### 2.1 How tokens reach React Native

1. **One TypeScript palette.** `@t3tools/shared/themePalettes` serves the web, the server and mobile; `mobileTheme.ts` derives the mobile roles from it ([mobileTheme.ts](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/apps/mobile/src/lib/mobileTheme.ts)).
2. **A generator writes committed CSS.** [`generate-uniwind-themes.mts`](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/apps/mobile/scripts/generate-uniwind-themes.mts#L221-L240) emits `generated-uniwind-themes.css`. Its `@layer theme { :root { … } }` holds `@variant light`, `@variant dark`, and a `@variant <theme>-light` and `<theme>-dark` pair per named theme. It also writes the theme-name list Metro passes as `extraThemes` ([metro.config.js](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/apps/mobile/metro.config.js#L115-L118)), a default-variables JSON and the sign-in widget's theme. `global.css` imports `tailwindcss`, `uniwind` and that file ([global.css](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/apps/mobile/global.css)).
3. **Checks.** The generator has a `--check` mode, and [a unit test](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/apps/mobile/scripts/generate-uniwind-themes.test.ts) asserts that every theme declares the same variables, as Uniwind requires. CI runs only the GraphQL `generate --check` steps, not this one ([ci.yml](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/.github/workflows/ci.yml#L106-L111)).
4. **Runtime.** `ScopedTheme` and `ScopedVariables` wrap the app, and `Uniwind.updateCSSVariables` handles Material You and user themes ([AppearancePreferencesProvider.tsx](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/apps/mobile/src/features/settings/appearance/AppearancePreferencesProvider.tsx#L348-L350)). `useResolveClassNames` turns classes into style objects for APIs that take only styles, such as navigation options. `withUniwind` wraps third-party components. `*ClassName` props with `accent-*` classes feed color props, and `useControlTheme` hands raw colors to native controls.

Uniwind's own rules match: Tailwind v4 only, all config in `global.css`; every theme must define the same variables; color props that aren't styles need `accent-*` classes; `withUniwind` is for third-party components only. Themes are `@variant` blocks in `@layer theme`, custom ones registered in `extraThemes`, and `oklch()` and `color(display-p3 …)` values are converted for native ([Uniwind skill](https://github.com/uni-stack/uniwind/blob/main/skills/uniwind/SKILL.md), [theming](https://github.com/uni-stack/uniwind/blob/main/skills/uniwind/references/theming.md)). Its first-party references don't mention `PlatformColor` or `DynamicColorIOS`, which [design-system.md](design-system.md) §1.4 relied on for increased contrast under Unistyles. Expo's Tailwind guide names NativeWind or Uniwind for native support ([guide](https://github.com/expo/expo/blob/main/docs/pages/guides/tailwind.mdx)). **H**

## 3. T3 Code's showcase and catalog

- **The catalog is the workshop.** [`ComponentCatalogScreen`](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/apps/mobile/src/features/development/ComponentCatalogScreen.tsx) renders the kit (buttons, list rows, chips, menus, sheets, dialogs, segmented controls, sliders, number fields, notices, app bars) under a theme picker covering every palette. It is registered only in development builds, at the deep link `dev/components` ([Stack.tsx](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/apps/mobile/src/Stack.tsx#L478-L485)). **H**
- **`mobile-showcase` is a store-screenshot pipeline.** `pnpm screenshots:mobile` seeds an isolated SQLite environment with demo projects, threads and terminal output ([environment](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/scripts/mobile-showcase-environment.ts)). It builds a Debug simulator app, starts Metro on a dedicated port with `EXPO_PUBLIC_SHOWCASE=1`, sets the simulator's appearance and status bar, and opens six scenes by deep link. Once the app writes a ready marker, it captures with `simctl io screenshot` and checks each image against App Store and Google Play sizes ([mobile-showcase.ts](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/scripts/mobile-showcase.ts), [config](https://github.com/pingdotgg/t3code/blob/6417151c093e54dbba0e6c824c69d03983793b9a/scripts/mobile-showcase.config.ts)). **H**
- **It runs on demand.** The workflow takes `workflow_dispatch` only, with platform, appearance and theme inputs. iOS runs on a third-party 12-vCPU macOS 26 runner with a 60-minute timeout, 300 when capturing every palette, and installs AXe and agent-device 0.21.25. ## 5. impeccable's live mode and critique

### 5.1 How they work

- **Live mode.** You select elements in the browser, pick an action and get AI-generated HTML and CSS variants, hot-swapped by the dev server's HMR. It needs "a running dev server with HMR (Vite, Next.js, Bun, etc.), OR a static HTML file" and a local checkout ([live.md](https://github.com/pbakaus/impeccable/blob/skill-v4.8.1/plugin/skills/impeccable/reference/live.md)). Setup writes `.impeccable/live/config.json`. Its `files` are "the HTML files the browser actually loads", injected before an anchor such as `</body>` with a script from a helper on `http://localhost:8400`. `node_modules/**` is hard-excluded. A Vite single-page app uses `index.html` ([live-setup.md](https://github.com/pbakaus/impeccable/blob/skill-v4.8.1/plugin/skills/impeccable/reference/live-setup.md)).
- **Wrapping and accepting.** To wrap a picked element, the helper finds its source by id, classes, tag and text, then writes a wrapper holding three variants into that file; TSX works, with the `<style>` inside a template literal. When it can't place the element (`element_not_found`, `element_not_in_source`), the agent takes over (`fallback: "agent-driven"`). On accept, the chosen variant is stitched into the source ("carbonize"). The agent then moves its CSS "into the project's real stylesheet" and unwraps it (live.md). With a Tailwind kit, that last step means rewriting the CSS into utilities or variants (judgment).
- **Web only.** "`live`, `generate`, and the bundled `impeccable detect` are web-only. If `setup.platform` is `ios`, `android`, or `adaptive`, don't lead with any of them" ([routing.md](https://github.com/pbakaus/impeccable/blob/skill-v4.8.1/plugin/skills/impeccable/reference/routing.md)). The detector hook returns early on the same three values ([hook_lib.rs](https://github.com/pbakaus/impeccable/blob/skill-v4.8.1/crates/hook/src/hook_lib.rs), `is_native_platform`). Shoestring's `PRODUCT.md` says `adaptive`, so today they are off for the web kit too. impeccable keeps `adaptive` for "one product that genuinely adapts its design language per OS" and says "a native wrapper around a website does not make its design language native" ([init.md](https://github.com/pbakaus/impeccable/blob/skill-v4.8.1/plugin/skills/impeccable/reference/init.md)), so the Electron app counts as web.
- **Which `PRODUCT.md`.** In a monorepo, `PRODUCT.md` and `DESIGN.md` resolve per workspace first, then at the repository root, file by file ([CLI contract](https://github.com/pbakaus/impeccable/blob/skill-v4.8.1/docs/CLI-CONTRACT.md), "Project / repo root resolution"). The hook resolves from the session's directory when it holds `.git`, `package.json` or `.impeccable` (`resolve_cache_cwd` in hook_lib.rs), so a session at the repository root reads the root file. **H**
- **Critique.** Two isolated assessments. A is a design review: source plus visual inspection. B is evidence: `impeccable detect --json` over markup files, and a browser overlay that injects `detect.js` into a fresh tab of the target URL. On native platforms only A runs, and the detector is skipped ([critique.md](https://github.com/pbakaus/impeccable/blob/skill-v4.8.1/plugin/skills/impeccable/reference/critique.md)). **H**
- **No workshop integration.** impeccable counts `storybook` and `@storybook/*` dependencies as signs of a UI workspace, scans `.storybook/`, and skips `storybook-static` (CLI contract; [bake.rs](https://github.com/pbakaus/impeccable/blob/skill-v4.8.1/crates/live/src/bake.rs)). `extract` ends with "Update any Storybook or component catalog" ([extract.md](https://github.com/pbakaus/impeccable/blob/skill-v4.8.1/plugin/skills/impeccable/reference/extract.md)). `component-review` reviews the raster plates of comp-led builds, not components ([component-review.md](https://github.com/pbakaus/impeccable/blob/skill-v4.8.1/plugin/skills/impeccable/reference/component-review.md)). Skill and CLI 4.8.1 shipped on 2026-11-08 ([releases](https://github.com/pbakaus/impeccable/releases)). **H**

## 6. The token pipeline

- **Web: Terrazzo 2.10 already fits.** `@terrazzo/plugin-tailwind` "can generate a Tailwind v4 Theme from your design tokens" through a template you own. `@tz (modifier: "value")` injects plugin-css's variables for one resolver permutation, for instance inside `@theme`, `@variant dark` or a `@custom-variant` for each high-contrast mode. Every permutation must also be listed in plugin-css's `permutations`. Composite typography tokens expand to Tailwind's `--text-*--line-height` convention, and `variableName` renames variables ([Tailwind integration](https://github.com/terrazzoapp/terrazzo/blob/main/www/src/pages/docs/integrations/tailwind.md)). Version 2.10.0, 2026-10-21. **H**
- **Web workshops consume it the same way.** Each imports the app's CSS. Theme switching is `withThemeByDataAttribute` or `withThemeByClassName` in Storybook, `data-theme` on `<html>` in Ladle, and a decorator in Cosmos. Terrazzo's template example offers `@custom-variant dark ([data-theme="dark"] &)`, which suits all three (judgment). For token documentation, Swatchbook 2.2.0, a third-party Storybook addon built on Terrazzo's parser, adds a toolbar switcher per resolver modifier and token doc blocks. It peers on Storybook `^10.1.0`, is MIT-licensed and has 27 stars ([Terrazzo's Storybook page](https://github.com/terrazzoapp/terrazzo/blob/main/www/src/pages/docs/integrations/storybook.md), [repo](https://github.com/unpunnyfuns/swatchbook)). **H**
- **React Native: no Terrazzo plugin.** The packages are CSS, CSS-in-JS, JS, Sass, Swift, Tailwind, token listing and vanilla-extract ([packages](https://github.com/terrazzoapp/terrazzo/tree/main/packages)). Three options:
  - **Uniwind**, T3 Code's choice: it reads Tailwind 4 CSS. A second plugin-tailwind template shaped like its `@layer theme { :root { @variant light {…} @variant dark {…} } }` block, or a small in-repo plugin, could feed it (unverified). Increased contrast would become extra registered themes, since Uniwind exposes no dynamic iOS colors (judgment).
  - **NativeWind 5.0.0-rc.1** (an RC, 2026-11-02, on Tailwind `>4.1.11`).
  - **Unistyles 3.8.1**, the TypeScript-theme route the earlier design-system note chose, which keeps `DynamicColorIOS`.

  T3 Code itself skips DTCG: one TypeScript palette feeds a generator. **M**
- **SwiftUI: no change.** `@terrazzo/plugin-swift` 0.3.4 is "still experimental" and generates asset catalogs ([Swift integration](https://github.com/terrazzoapp/terrazzo/blob/main/www/src/pages/docs/integrations/swift.md)); [design-system.md](design-system.md) §1.2 found it color-only and light/dark-only. ADR 0014's custom plugin stays. No workshop compared here renders SwiftUI; the watch keeps Xcode previews. **H**

## 7. Visual regression

- **Storybook's built-in visual tests are Chromatic**, a cloud service, through `@chromatic-com/storybook` ([visual tests](https://github.com/storybookjs/storybook/blob/v10.6.6/docs/writing-tests/visual-testing.mdx)). Its plans: free with 5,000 snapshots a month in Chrome; Starter at $179 a month; "Free for open source" on request ([pricing](https://www.chromatic.com/pricing)). Its CI step needs a project token. **H**
- **Self-hosted on the web.**
  - Vitest 5.1 compares screenshots with `toMatchScreenshot`. It waits for stable screenshots, and recommends generating references in CI, in Docker, or with a cloud service, because rendering differs across machines ([Vitest](https://github.com/vitest-dev/vitest/blob/v5.1.0/docs/guide/browser/visual-regression-testing.md)).
  - Storybook stories reach it through portable stories (`composeStories`) ([snapshot testing](https://github.com/storybookjs/storybook/blob/v10.6.6/docs/writing-tests/snapshot-testing.mdx)). A play function's `expect` is Storybook's own, so screenshot assertions belong in separate Vitest files (judgment; [issue 33153](https://github.com/storybookjs/storybook/issues/33153)).
  - Playwright `toHaveScreenshot` over a built Storybook's iframe works too ([end-to-end](https://github.com/storybookjs/storybook/blob/v10.6.6/docs/writing-tests/integrations/stories-in-end-to-end-tests.mdx)).
  - Ladle documents Playwright over `meta.json` ([visual snapshots](https://github.com/tajo/ladle/blob/main/packages/website/docs/visual-snapshots.md)).
  - Cosmos documents screenshots of detached renderer URLs from `getFixtures`, an experimental API ([Node API](https://github.com/react-cosmos/react-cosmos/blob/main/docs/pages/docs/node-api.mdx)). **H**
- **On the iPhone.**
  - Storybook for React Native: "there isn't a built-in way to do visual testing". Its docs script Maestro to open each story by `STORYBOOK_STORY_ID` deep link, take screenshots and compare them ([testing](https://github.com/storybookjs/react-native/blob/v10.7.1/docs/docs/intro/testing.md)).
  - The same approach fits a catalog route. Maestro 2.12.1 (2026-11-02), already pinned in the devshell, has `assertScreenshot` ([changelog](https://github.com/mobile-dev-inc/maestro/blob/main/CHANGELOG.md)).
  - React Native Harness 1.7.0 renders a component as an overlay in the real app environment and asserts `toMatchImageSnapshot` ([UI guide](https://github.com/callstackincubator/react-native-harness/blob/main/packages/cli/skills/ui.md)). **H**
- **For Shoestring (judgment).** Chromatic would need its token on pull requests, but [`factory.md`](../factory.md) puts secrets only in environments bound to `main` and `v*` tags. Baselines in git need no account. Both paths stay in `factory.md`'s deferred list until a bug shows the gap. **M**

## 8. CI cost

- **Runner minutes are free.** "GitHub Actions usage is free for standard GitHub-hosted runners in public repositories" ([billing](https://docs.github.com/en/actions/concepts/billing-and-usage)). The costs that matter are critical-path time ([`factory.md`](../factory.md): under 10 minutes for a TypeScript-only pull request, under 30 for a native one) and macOS capacity. **H**
- **Web.** The Storybook build and story tests join the `web` job, which already runs in the pinned Playwright image, where screenshot references stay stable (judgment). Durations are unmeasured. **L**
- **iPhone.** Catalog captures need the `apple` job: a simulator plus a Debug build. They fit the job's path filter (kit or native changes) or an on-demand workflow, as T3 Code runs its showcase. T3 Code runs on third-party macOS runners; Shoestring uses GitHub's free ones. Judgment. **M**
- **Ruled out on cost.** Chromatic (secrets, above) and paid runners. EAS is a separate open question in the charting decisions. **H**
