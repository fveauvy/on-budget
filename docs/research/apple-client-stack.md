## Question

Which client stack, local persistence, architecture, project setup, auth scheme, backend, hosting and distribution path should `on-budget` use? Targets: a daily-use, native-feeling iPhone + Mac budgeting app; offline-first with sync to an owned API and database; Face ID / Touch ID protection for bank data; server-side bank ingestion and push alerts; ≤ ~20 friends and family in France. Built by one developer working mostly through AI coding agents (Claude Code, Codex).

## TL;DR

1. *Superseded (see status).* **Client: SwiftUI multiplatform.** Swift 6.4, Xcode 27.2, deployment floor **iOS 26.0 / macOS 26.0**, newer APIs behind `if #available`. It is the only option where WidgetKit, App Intents, LocalAuthentication/Keychain, Liquid Glass and Mac conventions need no bridge. **Confidence: high.**
2. *Superseded (see status).* **Persistence: SQLite through GRDB 7.12**, optionally with **SQLiteData 1.12** on top for `@FetchAll`-style SwiftUI observation. Not SwiftData: its only built-in sync is CloudKit, and sync to your own server would be hand-built on its history API. **Medium-high.**
3. *Superseded (see status).* **Architecture and project:** `@Observable` feature models with injected dependency clients, no TCA until 2.0 is public. Code lives in **local Swift packages**, with a thin **`.xcodeproj` using buildable folders**; no project generator unless pbxproj conflicts actually show up. **Medium.**
4. **Auth:** **passkeys** on your own domain plus single-use **invites**. The server issues a short-lived access token and a rotating refresh token bound to a **Secure Enclave device key**, which signs standard **DPoP proofs** whose `jti` makes replays fail. App lock uses `LAPolicy.deviceOwnerAuthentication`, and sensitive actions require a fresh passkey assertion. The scheme is Apple-only: the watch has no passkey API and enrolls through the iPhone, and the web app has no Secure Enclave, uses a cookie session and must be served under the RP ID host (§3.3). Sign in with Apple is optional; Developer ID Mac builds can't use it. Access is modelled as households and ledgers (§3.3). **Medium-high.**
5. **Backend:** **Swift 6.4 + Hummingbird 2.28**, sharing a `Domain` package and an OpenAPI contract with the apps. **PostgreSQL 18**, **APNSwift 8** with token auth plus standard **Web Push** for web-app users, swift-jobs for ingestion and alerts, shipped as a static Linux binary with a CA bundle. Weakest part: swift-webauthn, still beta and checking a single origin. With a shared UI codebase that isn't Swift, the shared-package argument shrinks to the watch app (§4.1). Runner-up: TypeScript (Node 26 LTS or Bun 1.4, Hono 4.13 with 5.0 at RC, Drizzle). **Medium.**
6. **Hosting:** `PRODUCT.md` now sets a **dedicated EU VPS on a dedicated domain from day one**. That also solves what a Tailscale-only home server couldn't: App Review needs a live backend, the web app can't use the passkeys from a `*.ts.net` origin, and Android and Windows friends would need Tailscale too. Target: about €12–20/month in Paris or Germany (Scaleway DEV1-S ≈ €12 with IPv4 and a 20 GB volume; Hetzner CPX12 €11.99 or CPX22 €19.99, Cost-Optimized shown unavailable), plus off-site backups. The home server stays a development host (judgment). **Medium.**
7. **Distribution: TestFlight now, unlisted App Store later, the web app as the fallback.** An internal group for your household (no review; every tester needs an App Store Connect role, at least Developer or Marketing limited to the app). An external group for friends: the first build gets a TestFlight review, which needs a live backend and a way in for the reviewer, and Guideline 2.2 expects TestFlight apps to be "intended for public distribution". Unlisted distribution suits a limited audience, but it is a request Apple can decline. Automate uploads, because builds expire after 90 days; Xcode Cloud includes 25 h/month. Developer ID only as a Mac fallback. **Medium.**

## 2. If SwiftUI

### 2.1 Minimum OS targets

- On 2026-06-07, iOS 26 ran on 79% of all iPhones and 86% of iPhones introduced in the last four years ([Apple](https://developer.apple.com/support/app-store/)). No iOS 27 figure is published yet.
- iOS 27 keeps iOS 26's device list (iPhone 11 and later) (secondary, [AppleInsider](https://appleinsider.com/articles/26/06/08/ios-27-keeps-iphone-11-and-newer-compatibility)). macOS 27 is Apple silicon-only (secondary, [AppleInsider](https://appleinsider.com/articles/26/06/08/macos-27-compatibility-list-focuses-entirely-on-apple-silicon)). With a macOS 27 deployment target, Xcode 27 drops x86_64 from the default architectures ([Xcode 27 RN](https://developer.apple.com/documentation/xcode-release-notes/xcode-27-release-notes)).
- A 27 floor would remove `#available` checks for SwiftUI `reorderable()`, swipe actions on any container, `alert(item:)` and `alert(error:)` and the new toolbar APIs ([SwiftUI updates](https://developer.apple.com/documentation/updates/swiftui)). It would also unlock SwiftData's `ResultsObserver` and `HistoryObserver`, both iOS 27+ ([SwiftData updates](https://developer.apple.com/documentation/updates/swiftdata)). Apple ties the new `@State` macro to building with Xcode 27; the page doesn't say whether it depends on the deployment target.

| Floor | For | Against |
|---|---|---|
| **iOS 26 / macOS 26 (pick)** | Liquid Glass APIs are native ([2025 updates](https://developer.apple.com/documentation/updates/swiftui)); covers every iOS-27-capable iPhone plus un-updated ones, and Intel Macs on Tahoe | `#available` branches for 2027 APIs |

- **Rules that hold for any engine:** globally unique primary keys (UUIDs, never autoincrement), primary keys on every table, and careful uniqueness constraints. ### 2.3 App architecture

- **Observation-based MV/MVVM (pick).** One `@MainActor @Observable` model per feature ([Observation](https://developer.apple.com/documentation/observation), iOS 17 / macOS 14), owned by the parent and passed down. Dependencies (`APIClient`, `Database`, `SyncEngine`, `Keychain`, `Clock`) are protocols or structs of closures injected at the app root, each with live, preview and test variants. Views hold no business logic. Test models with Swift Testing against an in-memory database. This is the plain-Swift pattern agents get right most often (judgment).
- **TCA.** The latest public release is 1.26.2 ([releases](https://github.com/pointfreeco/swift-composable-architecture/releases)). Point-Free calls 2.0 "a fundamental redesign" (`@Feature`, `store.addTask`, new testing); since 2026-04-01 it has been a beta preview for paid "Point-Free Max" members ([post](https://www.pointfree.co/blog/posts/206-beta-preview-composablearchitecture-2-0)). Adopting 1.x today means a planned migration; adopting 2.0 means a paid beta. Revisit TCA when 2.0 ships publicly. **Confidence: medium.**

### 2.4 Modularization with local packages

Apple recommends local packages for modularity ([doc](https://developer.apple.com/documentation/xcode/organizing-your-code-with-local-packages)). Package tests run with `swift test`, which in Xcode 27 adds failure summaries and repeat-until runs ([Xcode 27 RN](https://developer.apple.com/documentation/xcode-release-notes/xcode-27-release-notes)), and they give agents fast loops without a simulator.

## 3. Auth and security

### 3.1 Platform facts

- **LocalAuthentication.** `.deviceOwnerAuthentication` accepts biometry, Apple Watch or the device passcode; `.deviceOwnerAuthenticationWithBiometrics` refuses the passcode fallback ([LAPolicy](https://developer.apple.com/documentation/localauthentication/lapolicy)). Biometrics-or-companion policies arrived in iOS 18 / macOS 15 ([doc](https://developer.apple.com/documentation/localauthentication/lapolicy/deviceownerauthenticationwithbiometricsorcompanion)). `NSFaceIDUsageDescription` is mandatory; Face ID starts scanning immediately, so warn in the UI; always provide a fallback ([Apple](https://developer.apple.com/documentation/localauthentication/logging-a-user-into-your-app-with-face-id-or-touch-id)). Detect enrollment changes with `LADomainState` (iOS 18 / macOS 15); `evaluatedPolicyDomainState` is deprecated ([LADomainState](https://developer.apple.com/documentation/localauthentication/ladomainstate), [deprecation](https://developer.apple.com/documentation/localauthentication/lacontext/evaluatedpolicydomainstate)). Neither the companion policies nor `LADomainState` exist on watchOS. The watch uses `.deviceOwnerAuthenticationWithWristDetection` (watchOS 9+), which fails if no watch passcode is set or the watch has left the wrist ([doc](https://developer.apple.com/documentation/localauthentication/lapolicy/deviceownerauthenticationwithwristdetection)).
- **Keychain access control.** Flags: `userPresence`, `biometryAny`, `biometryCurrentSet`, `devicePasscode`, `companion` (iOS 18, macOS 15, watchOS 11) and `privateKeyUsage` ([flags](https://developer.apple.com/documentation/security/secaccesscontrolcreateflags), [companion](https://developer.apple.com/documentation/security/secaccesscontrolcreateflags/companion)). `watch` is macOS-only (10.15+) and deprecated in macOS 15 in favor of `companion`, so it is no option for the iPhone app ([watch](https://developer.apple.com/documentation/security/secaccesscontrolcreateflags/watch)).
  - **Sync and backups.** `…ThisDeviceOnly` items never sync to iCloud Keychain and never restore onto a different device ([Apple](https://developer.apple.com/documentation/localauthentication/accessing-keychain-items-with-face-id-or-touch-id), [AfterFirstUnlockThisDeviceOnly](https://developer.apple.com/documentation/security/ksecattraccessibleafterfirstunlockthisdeviceonly)). Only `WhenPasscodeSetThisDeviceOnly` items are left out of backups. The other `ThisDeviceOnly` classes, including the `AfterFirstUnlockThisDeviceOnly` class §3.3 uses for the refresh token and push key, are backed up wrapped with the device UID and come back only when the same device is restored ([Platform Security](https://support.apple.com/guide/security/keychain-data-protection-secb0694df1a/web)).
  - **Passcode.** `WhenPasscodeSetThisDeviceOnly` can't store items without a passcode, and removing the passcode deletes them ([doc](https://developer.apple.com/documentation/security/ksecattraccessiblewhenpasscodesetthisdeviceonly)).
  - A Touch ID unlock can be reused for up to 5 minutes ([Apple](https://developer.apple.com/documentation/localauthentication/accessing-keychain-items-with-face-id-or-touch-id)).
  - **macOS.** Always set `kSecUseDataProtectionKeychain = true` ([doc](https://developer.apple.com/documentation/security/ksecusedataprotectionkeychain)). Its access groups come from entitlements that "must be authorized by a provisioning profile", embedded in an app-like bundle ([TN3137](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains)). A Developer ID build therefore needs a Developer ID provisioning profile (§5).
- **Secure Enclave.** Through the Security framework (`SecKey`), keys are P-256 only, generated inside the enclave and never imported or exported. Signing needs `privateKeyUsage`. `WhenUnlockedThisDeviceOnly` is preferred "unless your app operates in the background" ([Apple](https://developer.apple.com/documentation/security/protecting-keys-with-the-secure-enclave)). Since iOS, macOS and watchOS 26, CryptoKit's `SecureEnclave` also creates ML-KEM-768/1024 and ML-DSA-65/87 keys; `SecureEnclave` itself exists from watchOS 6 ([CryptoKit](https://developer.apple.com/documentation/cryptokit/secureenclave)). P-256 stays the right choice for ES256 DPoP proofs (judgment).
- **Data Protection.** iOS file classes are `complete`, `completeUnlessOpen`, `completeUntilFirstUserAuthentication` (the default) and `none`. Background work needs a non-`complete` class ([Apple](https://developer.apple.com/documentation/uikit/encrypting-your-app-s-files), [FileProtectionType](https://developer.apple.com/documentation/foundation/fileprotectiontype)). On Apple silicon Macs, Data Protection defaults to class C with a volume key, FileVault is on by default from macOS 26.4, and apps can opt in to per-file classes ([Platform Security](https://support.apple.com/guide/security/data-protection-overview-secf6276da8a/web)).
- **Passkeys.** Registration and assertion need an associated domain with the `webcredentials` service ([Apple](https://developer.apple.com/documentation/authenticationservices/supporting-passkeys)). Since iOS 14 / macOS 11, devices fetch `/.well-known/apple-app-site-association` through Apple's CDN, so the file must be on public HTTPS with a valid certificate and no redirects. The CDN fetches it within 24 h, and devices re-check about weekly ([associated domains](https://developer.apple.com/documentation/xcode/supporting-associated-domains)). The alternate modes that bypass the CDN cover only development-signed apps on devices in developer mode (`developer`) or MDM-managed devices (`managed`) ([entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.associated-domains)). **So TestFlight builds need a public domain for the association file, even if the API stays private.** iOS/macOS 26 add a passkey account-creation API ([ASAuthorizationAccountCreationProvider](https://developer.apple.com/documentation/authenticationservices/asauthorizationaccountcreationprovider)). The passkey API itself, `ASAuthorizationPlatformPublicKeyCredentialProvider`, exists on iOS 15, macOS 12, tvOS 16 and visionOS 1, not on watchOS ([Apple](https://developer.apple.com/documentation/authenticationservices/asauthorizationplatformpublickeycredentialprovider)).
- **Sign in with Apple (SIWA).** Developer ID–signed Mac apps can't use it; associated domains, push and Time Sensitive notifications all work there ([macOS capabilities](https://developer.apple.com/help/account/reference/supported-capabilities-macos)). The client secret is an ES256 JWT whose `exp` is at most 6 months ahead, so it needs rotation ([Apple](https://developer.apple.com/documentation/accountorganizationaldatasharing/creating-a-client-secret)). Server-to-server notifications (`consent-revoked`, `account-deleted`, email relay changes) need a public TLS 1.2+ endpoint ([Apple](https://developer.apple.com/documentation/signinwithapple/processing-changes-for-sign-in-with-apple-accounts)).
- **App Review.** Guideline 4.8 requires an equivalent privacy-preserving login only if you offer third-party or social login. Guideline 5.1.1(v) requires in-app account deletion when the app supports account creation ([guidelines](https://developer.apple.com/app-store/review/guidelines/)). TestFlight external builds are reviewed against these guidelines too ([TestFlight](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview)). Review needs backend services "live and accessible during review" and "either an active demo account or fully-featured demo mode" (Before You Submit); guideline 2.1(a) accepts a demo mode instead of a demo account only "with prior approval by Apple" ([guidelines](https://developer.apple.com/app-store/review/guidelines/)). Passkey-only sign-in behind 72 h single-use invites gives a reviewer no way in, so keep a long-lived reviewer invite into a demo household with synthetic data (judgment).

### 3.2 Server-side verification and sessions

- **SIWA.** Verify the identity token's ES256 signature against Apple's JWKS (`GET https://appleid.apple.com/auth/keys`, pick the key by `kid`), then `nonce`, `iss = https://appleid.apple.com`, `aud = client_id` and `exp` ([verifying](https://developer.apple.com/documentation/signinwithapple/verifying-a-user), [keys](https://developer.apple.com/documentation/signinwithapplerestapi/fetch-apple%27s-public-key-for-verifying-token-signature)). Exchange the authorization code at `/auth/token` for a refresh token, which you may re-validate at most once a day ([token validation](https://developer.apple.com/documentation/signinwithapplerestapi/generate-and-validate-tokens)). Revoke it at `/auth/revoke` when the account is deleted ([revoke](https://developer.apple.com/documentation/signinwithapplerestapi/revoke-tokens)). After verification, Apple leaves session management to you.
- **Passkeys (WebAuthn).** The server issues a random single-use challenge and an opaque `user.id`. It then verifies `type`, the challenge, the `origin` against every expected origin, the RP ID hash, the user-presence and user-verification flags, and the signature over `authenticatorData ‖ hash(clientDataJSON)`. The RP "MUST NOT accept unexpected values of origin" (WebAuthn §13.4.9). Store the credential ID, public key and backup flags ([WebAuthn L3](https://www.w3.org/TR/webauthn-3/), a W3C Recommendation since 2026-08-25). Libraries: [swift-webauthn](https://github.com/brokenhandsio/swift-webauthn) 1.0.0-beta.2 (2026-11-06), [SimpleWebAuthn](https://github.com/MasterKale/SimpleWebAuthn) 14.1 (TS; `expectedOrigin` takes one origin or a list), [go-webauthn](https://github.com/go-webauthn/webauthn) 0.18.2.
  - **swift-webauthn has moved.** `github.com/swift-server/swift-webauthn` now redirects to `brokenhandsio/swift-webauthn`, which isn't on the SSWG incubated list ([SSWG](https://www.swift.org/sswg/incubated-packages.html)). Its `Configuration` takes a single `relyingPartyOrigin` string, and verification requires `origin == relyingPartyOrigin` ([source](https://github.com/brokenhandsio/swift-webauthn/blob/1.0.0-beta.2/Sources/WebAuthn/WebAuthnManager+Configuration.swift)). The [Hummingbird example](https://github.com/hummingbird-project/hummingbird-examples/tree/main/webauthn) still depends on `swift-server/webauthn-swift` from `1.0.0-alpha.2`. All of this adds to the beta risk.
- **Sessions.** RFC 9700: refresh tokens for public clients "MUST be sender-constrained or use refresh token rotation" ([RFC 9700](https://www.rfc-editor.org/rfc/rfc9700)). Do both: rotate on every use, and bind to a device key with DPoP ([RFC 9449](https://www.rfc-editor.org/rfc/rfc9449)). Use standard DPoP proof JWTs (`jti`, `htm`, `htu`, `iat`, plus `ath` alongside an access token), not a custom signature: a proof with no unique ID can be replayed for as long as the server accepts it. Servers "can store the jti value of each DPoP proof" for that window "to prevent multiple uses", and a server-provided `nonce` narrows the window further (RFC 9449 §11.1).

### 3.3 Proposed scheme for on-budget

**Identity and enrollment**
1. You (as admin) create a single-use invite with a 72 h TTL, bound to a household and a role, and share it as a QR code or universal link.
2. The app sends the invite and gets registration options, creates a passkey (RP ID on the dedicated domain that `PRODUCT.md` requires, written `<rp-id>` below, e.g. `on-budget.<your-domain>`), and generates a Secure Enclave device key (P-256, `privateKeyUsage`, `AfterFirstUnlockThisDeviceOnly`).
3. The server verifies everything and creates the `user`, a `device` (public key, platform, APNs token later) and a session.
4. A Mac or second iPhone signs in with the same passkey through iCloud Keychain, and registers its own device key.
5. The watch can't create or use passkeys (§3.1). It enrolls through the paired iPhone with its own Secure Enclave key and a narrower refresh token ([watchos-app.md](watchos-app.md) §2.7). The web app signs in with the same passkey and gets an HttpOnly cookie session, not a device-bound refresh token ([web-client-sync.md](web-client-sync.md) §4.3).

Choose the RP ID domain once: credentials are scoped to it ([WebAuthn L3](https://www.w3.org/TR/webauthn-3/)), so changing it later strands every passkey. The public VPS can serve the association file; a static public site also works if the API ever goes private (judgment). Recovery: the passkey comes back with the user's iCloud Keychain; if it can't, you issue a recovery invite, which suits friends and family.

**Web origin.** The RP ID must equal the page origin's effective domain or be a registrable suffix of it (WebAuthn §5.1.3), so the web app lives at `<rp-id>` or a subdomain of it. A `*.ts.net` origin (Serve or Funnel) can't use these passkeys unless `<rp-id>` lists it in a Related Origin Requests file at `/.well-known/webauthn` (WebAuthn §5.11; browser support not checked) ([WebAuthn L3](https://www.w3.org/TR/webauthn-3/)). Native Apple apps report `https://<rp-id>` as the origin (an Apple engineer on the [developer forums](https://developer.apple.com/forums/thread/719003), 2022; secondary). So either serve the web app at exactly `https://<rp-id>`, or verify against a list of origins. [web-client-sync.md](web-client-sync.md)'s `https://app.<rp-id>` makes two, which swift-webauthn beta.2 handles only with one manager per origin (judgment).

**Tokens and storage**

| Secret | Where | Protection | Why |
|---|---|---|---|
| Access token (15 min, opaque or signed) | Memory | n/a | Short-lived |
| Refresh token (opaque 256-bit, rotated, ~60-day sliding; stored hashed on the server, reuse revokes the device) | Data-protection Keychain, access group shared with extensions | `AfterFirstUnlockThisDeviceOnly`, no biometry flag | Background sync must read it |
| Device key | Secure Enclave | `privateKeyUsage`, `AfterFirstUnlockThisDeviceOnly`; signs a DPoP proof JWT (`jti`, `htm`, `htu`, `iat`, `ath`) on refresh and on writes; the server rejects a `jti` it has already seen | A stolen refresh token alone is useless, and a captured proof can't be replayed |
| Push-payload key (symmetric, per device) | Keychain, shared with the notification extension | `AfterFirstUnlockThisDeviceOnly` | Amounts and merchants never reach APNs in clear |
| Local database | App group container | Class C (default) on iOS; FileVault / class C on Mac | Widgets and background refresh |

**Backups.** The refresh token and the push key are in device backups, wrapped with the device UID, so they restore only to the same device (§3.1). Restoring an older backup onto the same iPhone brings back an already-rotated refresh token, so reuse detection revokes that device, and the app must fall back to a passkey sign-in (judgment).

**App lock and step-up**
- On cold start, and after more than 5 minutes in the background, call `evaluatePolicy(.deviceOwnerAuthentication)`. Show a privacy cover in the app switcher and in redacted widgets.
- This lock is a UI gate. The cryptographic protection comes from Data Protection and Keychain classes, because a biometry-gated database key would break widgets and background sync (judgment).
- Sensitive actions require a fresh passkey assertion with `userVerification = required`, checked by the server. Examples: adding or removing a bank connection, inviting or removing members, changing sharing, exporting data.
- The watch locks with its passcode and wrist detection and never offers sensitive actions ([watchos-app.md](watchos-app.md) §2.8).
- The web app has no LocalAuthentication, Keychain or Secure Enclave, so its lock and its step-up are both a WebAuthn assertion with `userVerification = required`. A non-extractable WebCrypto key could bind web tokens DPoP-style, since then "DPoP renders exfiltrated tokens alone unusable", but XSS can still sign with that key in place (RFC 9449 §2). That is why [web-client-sync.md](web-client-sync.md) §4.3 prefers an HttpOnly cookie session.

**Households, private accounts and a joint account.** `PRODUCT.md` asks for "private by default, shared by choice", an optional joint account, and isolated households. All three map onto one access model.

| Entity | Notes |
|---|---|
| `user` | Passkeys, optional `apple_sub`, devices |
| `household` | Isolation boundary; members have role `owner` or `member` |
| `ledger` | Sync and permission boundary. Three kinds: `personal` (one user; the default for new accounts), `household` (all members), `joint` (named users or households) |
| `ledger_access(ledger, principal, role)` | The principal is a user or a household; roles are `viewer`, `editor` and `admin` |
| `bank_connection` | Owned by the user who gave bank consent; only they can renew or delete it. It feeds accounts into the ledger they choose. |
| `account` | Belongs to exactly one ledger. Moving it to another ledger is the sharing action. |
| Budgets, categories, limits | Per ledger. A personal budget can count a share of a joint account, e.g. 50/50. |
| `alert_subscription(user, ledger, rule)` | The server evaluates the rule and pushes to that user's devices |

Example with two households:
- **H1 is the owner and the partner.** The owner's bank accounts start in the owner's personal ledger, and the partner's in the partner's. Both make their own choice to share.
- **A joint account opened later by the couple** goes into H1's household ledger, with both as editors.
- **H2 is a friend's household**, fully isolated: no `ledger_access` row involves both H1 and H2.
- **A joint account across households** (say, siblings in H1 and H2 who co-own one) gets a `joint` ledger. It has one access row per co-owner, created only once both accept an invite, and nothing else crosses.
- **Duplicates.** Each co-holder may connect the joint account from their own bank login; deduplicate on IBAN and keep one connection as the source (judgment; see [bank-aggregation.md](bank-aggregation.md) for joint-account access).

- Devices sync only the ledgers their user can reach. The server authorizes every change with a single `can(user, action, ledger)` check, covered by table-driven tests. Postgres row-level security adds defense in depth (judgment).
- Revoking access tombstones the `ledger_access` row, and clients purge that ledger's data on their next sync.
- Account deletion is in-app (guideline 5.1.1(v)), revokes SIWA tokens if SIWA was used, and transfers or closes bank connections.

**Confidence: medium-high** (standard building blocks; how the household model fits the sync note is untested).

### 4.3 APNs and iOS background limits

- **Token auth** ([Apple](https://developer.apple.com/documentation/usernotifications/establishing-a-token-based-connection-to-apns)): a `.p8` key with a 10-character Key ID. The JWT carries `alg ES256`, `kid`, `iss = Team ID` and `iat`. Refresh it no more than once every 20 min and no less than once every 60 min. Use separate sandbox and production team keys (at most two per environment). One connection serves one team.
- **Sending** ([Apple](https://developer.apple.com/documentation/usernotifications/sending-notification-requests-to-apns)): HTTP/2 + TLS 1.2 to `api.push.apple.com:443` (or port 2197), payload ≤ 4 KB. Set `apns-push-type`, and `apns-priority 10` for alerts. APNs stores at most one undelivered notification per bundle ID, for up to 30 days via `apns-expiration`. Outbound-only, so it works from a home server behind NAT. Since 2025-02-24, APNs production presents a new server certificate under the USERTrust RSA Certification Authority root, so the server's trust store must include it ([upcoming requirements](https://developer.apple.com/news/upcoming-requirements/)). A static binary in a minimal or `scratch` image has no system trust store, so ship a CA bundle that contains that root (judgment).
- **Background limits.** Background pushes are low-priority and not guaranteed; "don't try to send more than two or three per hour"; the app gets 30 s ([Apple](https://developer.apple.com/documentation/usernotifications/pushing-background-updates-to-your-app)). `BGAppRefreshTask` runs when the system decides, for up to 30 s; `BGProcessingTask` is for deferrable heavy work ([strategies](https://developer.apple.com/documentation/backgroundtasks/choosing-background-strategies-for-your-app)). `BGContinuedProcessingTask` (iOS 26) covers work that starts in the foreground and continues in the background, with progress shown in a cancellable Live Activity ([doc](https://developer.apple.com/documentation/backgroundtasks/bgcontinuedprocessingtask)). **So the server evaluates budget limits and upcoming bills and sends alert pushes; the client syncs in the foreground and opportunistically in the background.**
- **Privacy.** Send `mutable-content: 1` with an encrypted body, and decrypt it in a notification service extension, which has about 30 s ([Apple](https://developer.apple.com/documentation/usernotifications/modifying-content-in-newly-delivered-notifications)). Reserve the Time Sensitive level (breaks through Focus, users can turn it off; [doc](https://developer.apple.com/documentation/usernotifications/unnotificationinterruptionlevel/timesensitive)) for hard limits and bills due today.
- **Web Push for web-app users.** Friends on Android or Windows use the web app, which has no APNs device token, so the server also sends standard Web Push: Push API subscriptions, the HTTP push protocol ([RFC 8030](https://www.rfc-editor.org/rfc/rfc8030)), VAPID ([RFC 8292](https://www.rfc-editor.org/rfc/rfc8292)) and payload encryption ([RFC 8291](https://www.rfc-editor.org/rfc/rfc8291)). That encryption does the job of the per-device push key on the web (judgment). On iOS and iPadOS, Web Push reaches only web apps added to the Home Screen (16.4+), and permission must be asked "in response to direct user interaction" ([WebKit](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)). Details in [web-client-sync.md](web-client-sync.md) §5.4.
