## Question

The owner watched ["Why I'm no longer using Docker (on a VPS)"](https://youtu.be/zCzQ88aXV4g) (Dreams of Code, 2026-11-03, 16:54, sponsored by Hostinger; configuration repo [dreamsofcode-io/nixos-vps](https://github.com/dreamsofcode-io/nixos-vps)) and asked: can on-budget's web infrastructure use this approach? [ADR 0003](../adr/0003-nixos-just-tailscale-infrastructure.md) has since adopted it: NixOS in a flake, deployed with `just`, and "reachable only over Tailscale", with "Nothing may depend on inbound connections from the internet". This note checks the approach against on-budget's needs and turns it into a target design within that decision.

- **Server side:** an API + PostgreSQL for sync; a worker for bank fetches (at most 4 unattended per account per day, [bank-aggregation.md](bank-aggregation.md)), alert evaluation, APNs and Web Push; the web app (full parity, offline-first); an HTTPS bank-consent callback route, reached by the member's browser, so it works on the tailnet ([bank-aggregation.md](bank-aggregation.md) §4.5); the Apple association file, the only public file, on static hosting ([web-client-sync.md](web-client-sync.md) §5.2–5.3).
- **Decided:** a dedicated EU VPS from day one; a dedicated domain, not bought yet; bank data limited to transaction history. This note's brief accepted public exposure, but ADR 0003 and `PRODUCT.md` (Stack, "Private network friendly"), the recorded decisions, keep the reference deployment on Tailscale. This note follows them: the VPS has a public address, but only Tailscale's UDP port answers on it. Opening 80/443 would first need an ADR amending 0003 and `PRODUCT.md`; [Ingress](#ingress) lists what could justify it.
- **Constraints:** the repository is public, so personal infrastructure, identifiers and plaintext secrets stay out of it (`AGENTS.md`). Each instance has one owner and no public sign-up ([ADR 0001](../adr/0001-self-hosted-single-owner-instances.md)), so the maintainer's instance holds only the maintainer's households; earlier notes sized for ~20 friends, this one doesn't. Agents write most code. The backend language (TypeScript or Swift) is open. Deploys may start from a Mac, which can't build `x86_64-linux` natively.

## TL;DR

**Verdict: yes. Adopt the video's model (ADR 0003 already did), not the starter repo as it stands.** One pinned flake, apps built as Nix packages and run as hardened systemd units, sops-nix secrets, builds off the server, atomic switches and rollback to earlier generations all fit on-budget. The repo is a Hostinger-specific starter: its tailnet-only mode already matches ADR 0003, but public apps go through Cloudflare Tunnel, deploys run interactively from a laptop through a root-equivalent trusted user, and there is no TLS on the host, database, backup, monitoring, CI or VM test. Five changes make it fit (**M-H**):

1. **Split public and private.** The public repo ships packages, a `services.on-budget` NixOS module (app, backups, monitoring), VM tests and a host template (`nix flake init -t`). The maintainer's instance lives in a private ops repo made from that template, which pins on-budget as a flake input: `nix flake update on-budget` + `just deploy` is the video's two-command loop. (**H** on the rule; the layout is judgment)
2. **TLS on the VPS, tailnet only (ADR 0003); no Cloudflare Tunnel.** Caddy serves the web build from the Nix store, the bank callback and the API (over a Unix socket) on `app.<rp-id>`, whose A/AAAA records point to the VPS's Tailscale addresses. Its certificate comes from ACME DNS-01 (lego through `security.acme`), since no CA can reach the host. 443 and SSH are open only on `tailscale0`, and the public interface answers only Tailscale's UDP port, which requires `services.openssh.openFirewall = false` (the default, `true`, opens 22 on every interface). The association file alone is public, on static hosting. A tunnel would add a public path and decrypt every transaction at Cloudflare, a US processor; EU-only decryption is an Enterprise add-on. (**H** on the rules, **M** on the DNS and certificate setup)
3. **Install anywhere with nixos-anywhere + disko**, on an x86_64 EU KVM VPS with ≥ 4 GB: Hetzner CX23/CX33 (€5.99/€8.99) if Hetzner accepts new servers (restricted since 2026-06-26), OVHcloud VPS-1/VPS-2 (from €3.81/€7.21), or Hostinger KVM 2 for its ready NixOS template (KVM 1 has a single vCPU). x86_64, because CI's VM tests need KVM and GitHub's x64 runners have it. (**M**)
4. **Deploy from CI with deploy-rs, keep `just deploy` as the entry point.** CI builds on x86_64, runs the checks, joins the tailnet as `tag:ci`, copies a signed closure and activates with magic rollback (the host reverts unless SSH reconnects, within 30 s by default). A rollback runs the previous generation's deploy-rs script, which a generation installed by nixos-anywhere lacks, so the first deploy-rs deploy must be a harmless one. A Mac deploys only in emergencies, building on the VPS. (**M**)
5. **Add what neither source has:** PostgreSQL 18 set explicitly (26.05 defaults to 17), hourly encrypted `pg_dump`s with restic to two EU targets plus monthly restore drills, a restore epoch so that offline-first clients re-push what a restore lost, Healthchecks dead-man checks, weekly lock updates gated by VM tests, a reboot timer for kernel updates, and a NixOS upgrade every December and June. (**M-H**)

- **When:** 26.05 is supported until 2026-12-31; 26.11 is planned for 2026-11-30, already a week late. Install on 26.11, which a Swift 6 backend needs anyway (26.05 ships Swift 5.10.1). (**H**)
- **Cost:** about €10–15/month (VPS, Storage Box €3.20, a second backup target; domain extra), plus GitHub Pro for the private ops repo (about $4/month, unverified): on Free, a private repo gets neither environment secrets nor a `main`-only deploy rule. CI is free for the public repo, and the ops repo's runs should fit in the monthly Actions allowance ($12 on Free, $18 on Pro, about 2,000 or 3,000 Linux minutes). (**M**)
- **First step:** a deploy machine on a Nix release fixed for the 2026 advisories (≥ 2.35.3 or 2.34.9), flakes enabled, `ca-derivations` and `recursive-nix` off. For a store left user-owned by the old scripted installer, the advisory's fix is to upgrade and garbage-collect, or run its `chown` loop over the whole store; a reinstall is optional. (**H**)
- **Supersedes** factory-ci-quality.md's Kamal/Docker deploy and apple-client-stack.md §4.4's Postgres in Docker and public VPS. Record this design in an ADR that builds on 0003 and keeps its tailnet-only rule; amend 0003 and `PRODUCT.md` only if the owner opts for public access.

## What the video and repo do

Inputs: the auto-captions (narration only, no on-screen commands), the description, and every file of the repo at [`594211e`](https://github.com/dreamsofcode-io/nixos-vps/tree/594211ef75c2d9b0ea2a75dd6f1cdda26752550c) with its 36-commit history (2026-10-20 to 11-04). Nothing was executed. Timestamps come from the captions.

### The argument

- **Why he left Docker** [00:02–01:15]: after ~10 years of Docker on VPSs (Compose, Dokploy, image builds), all his production instances have run NixOS for a couple of months, prompted by the sponsor adding NixOS. NixOS manages containers well, but in a NixOS workflow Docker "was creating more problems than it was solving".
- **Workflow cost** [01:26–02:37]: a Docker redeploy is pull, build, unique tag, push to a registry, edit the container definition, rebuild. The NixOS one is two commands from his own machine, with no registry. Automation hides the steps but keeps the registry and its failure modes.
- **What NixOS gives** [03:35–05:52]: one declarative configuration, built on his machine, copied and activated. Unlike Ansible, the whole system is built before activation, so a failed build leaves the VPS unchanged. Generations allow rollback. Every change is reviewed in Git, "by my own hand or through an AI agent". The same configuration rebuilds a new VPS, bare metal or a local VM.
- **Why Docker undermines it** [06:59–09:11]: `oci-containers` (Podman by default) pulls images on the VPS *after* activation, so a missing tag fails mid-activation and the app goes down. A registry is third-party infrastructure (expired tokens, outages); copying or building images on the box breaks reproducibility; images are state outside the configuration.
- **Images into the Nix store, then no images** [09:24–13:08]: `dockerTools.pullImage` fetches at build time on his machine. `dockerTools.buildImage` builds from a Nix package, so each app repo gets a `flake.nix` and becomes an input of the VPS flake; an update is `nix flake update` + `just deploy`. Private repos come over his own SSH access, so no token sits on the VPS. Once apps are packages, he runs them as plain systemd services and deleted the containers module.
- **Isolation** [13:31–15:46]: systemd sandboxing and NixOS containers (private network and file system, optionally ephemeral, port forwarding, bind mounts, resource limits), hidden in his private production configuration behind a "service" abstraction: package, ports, SOPS file, environment, and an internal (Tailscale Serve) or external (Cloudflare Tunnel) ingress.
- **Limits** [15:50–16:21]: Docker stays for third-party apps shipped as images and for his k3s home lab.

### The repo's procedure

- **Pins:** `nixos-26.05` (`7dcdd873`) and sops-nix (`b18e01ce`), both locked 2026-11-02; `x86_64-linux` only; the configuration is always named `vps`; MIT licence.
- **Prerequisites:** Nix with `nix-command` and `flakes` (Lix suggested on macOS), just, Git, Bash, SSH, `$EDITOR`; SOPS and age come through Nix. Without those features enabled, the README's `nix shell nixpkgs#…` commands fail; the recipes pass `--extra-experimental-features` themselves.

```sh
ssh root@x.x.x.x true                           # Hostinger VPS on its NixOS template; check the fingerprint in the console
git clone https://github.com/dreamsofcode-io/nixos-vps.git && cd nixos-vps
nix run nixpkgs#mkpasswd -- --method=yescrypt   # sudo password only: SSH is key-only
"$EDITOR" settings.nix    # hostname, sshKeys, hashedPassword, access = "public", tailscale and cloudflared off
just bootstrap vps root@x.x.x.x                 # SOPS file encrypted to your age key + the VPS host key
git add secrets/vps.json                        # flakes only see tracked files
just deploy root@x.x.x.x                        # needs x86_64-linux; or: just deploy root@x.x.x.x vps <builder>
ssh admin@x.x.x.x 'whoami; hostname' && ssh -t admin@x.x.x.x 'sudo reboot'
ssh admin@x.x.x.x 'uname -r; systemctl --failed --no-pager'   # done when admin works and nothing failed
ssh -t admin@x.x.x.x 'sudo nixos-rebuild switch --rollback'   # rollback: supported, not in the repo
# Tailscale: single-use, non-ephemeral auth key stored as "tailscale-auth-key", tailscale.enable = true
just bootstrap vps admin@x.x.x.x && just deploy admin@x.x.x.x
just deploy admin@100.x.y.z                     # after setting access = "tailscale"
# Cloudflare Tunnel, locally managed; credentials JSON stored as "cloudflared-<uuid>.json"
cloudflared tunnel login && cloudflared tunnel create vps
jq -Rs . "$HOME/.cloudflared/TUNNEL_UUID.json"  # paste the output through just bootstrap
cloudflared tunnel route dns TUNNEL_UUID app.example.com && just deploy admin@x.x.x.x
```

- **Accounts and SSH** (`configuration.nix`): root login off, only `admin` (wheel), public key only, no password or keyboard-interactive login. Assertions fail the build without a usable hash and a non-blank key. `admin` is a Nix trusted user, "root-equivalent without the sudo password" (README).
- **`just bootstrap`:** reads `/etc/ssh/ssh_host_ed25519_key.pub` over an authenticated SSH session, converts it with `ssh-to-age`, creates or reuses the local age key, encrypts `{}` for both recipients and opens `sops`. It never re-keys and there is no `.sops.yaml`, so a replaced VPS means re-encrypting by hand. sops-nix decrypts into root-only `/run/secrets/<name>`.
- **`just deploy`** (`scripts/deploy.sh`): `ssh <target> true` to fail fast; `nix build .#nixosConfigurations.<name>.config.system.build.toplevel --no-update-lock-file`, locally or with `--eval-store auto --store ssh-ng://<builder>`; a store-path regex check; `nix copy --substitute-on-destination --no-check-sigs --to ssh-ng://<target>`; then `ssh -t <target> "sudo /run/current-system/sw/bin/nixos-rebuild switch --no-reexec --store-path '<path>'"`. Only the Python `nixos-rebuild` has `--store-path` (merged 2026-01-22), so the pre-installed image must be that recent.
- **Tailnet-only mode** (`modules/networking.nix`): asserts Tailscale, forces the firewall on, `mkForce`s every public TCP port away (80/443 included), opens Tailscale's UDP port, trusts `lo` and `tailscale0`, disables ping. Container forwarding and the tunnel aren't filtered.
- **Services** (README): `virtualisation.oci-containers`, whose example sets `backend = "docker"` and pulls `nginx:stable` at unit start (the very failure the video criticises; it shows `"podman"` as the alternative), or a `systemd.services.<name>` with `DynamicUser` and `StateDirectory`. Files under `modules/` and `services/` are auto-imported (`lib/import-directory.nix`). Secrets reach units through `LoadCredential` or `environmentFiles`.
- **Builders and more servers:** macOS can't build the system. The README offers nix-darwin's `nix.linux-builder` (x86_64 only by emulation on Apple silicon, slow) or a separate x86_64 Linux builder (`just deploy admin@x.x.x.x vps <host>`; `target` builds on the VPS, for recovery). A second server is `hosts/vps2.nix` plus `vps2 = mkVps (import ./hosts/vps2.nix) [];`.
- **Tests** (`tests/`, wired into neither `checks` nor CI): an eval-only assertion test and Python tests of the bootstrap, deploy and module-discovery logic with `nix` and `ssh` stubbed. Untested: a real build, a VM boot, the remote switch, both access modes, decryption on a host.

```nix
# A service secret (README); the app reads $CREDENTIALS_DIRECTORY/api-key
sops.secrets.api-key.restartUnits = [ "my-app.service" ];
systemd.services.my-app.serviceConfig.LoadCredential = "api-key:${config.sops.secrets.api-key.path}";
# Mac builder through nix-darwin: first pass, then the Apple-silicon second pass
nix.linux-builder.enable = true;
nix.linux-builder.systems = [ "aarch64-linux" "x86_64-linux" ];
nix.linux-builder.config.boot.binfmt.emulatedSystems = [ "x86_64-linux" ];
```
```sh
sudo darwin-rebuild switch --flake /path/to/your/mac-config#YOUR_MAC_NAME
just deploy admin@x.x.x.x vps <builder>         # separate x86_64 builder; "target" builds on the VPS
just bootstrap vps2 root@NEW_VPS_IP && git add hosts/vps2.nix secrets/vps2.json
just deploy root@NEW_VPS_IP vps2                # first deploy of a second server
nix eval --impure --json --expr 'import ./tests/admin-access.nix { flake = builtins.getFlake ("path:" + toString ./.); }'
python3 tests/deploy.py                         # also bootstrap-secrets.py and module-discovery.py
```

### Video vs repo

- **Only in the video:** `pullImage`/`buildImage`, app flakes as inputs, the update loop, packages under systemd, sandboxing beyond `DynamicUser`, NixOS containers, the service abstraction, Tailscale Serve, rollback and the local test VM.
- **Only in the repo:** the SOPS bootstrap, the SSH assertions, the tailnet-only mode, trusted-user deploys, remote builders, Hostinger's cloud-init and guest agent, the tests.
- **Timeline:** until 2026-10-23, `just deploy` built on the VPS itself (`nixos-rebuild-ng … --build-host "$target" --target-host "$target"`). Local builds and trusted users landed on publication day ([`24fb7df`](https://github.com/dreamsofcode-io/nixos-vps/commit/24fb7df)), and every copying deploy failed until [`57dcab6`](https://github.com/dreamsofcode-io/nixos-vps/commit/57dcab6) (2026-11-04) because `nix copy` was given `--use-substitutes`. The README describes the state after the video.
- **Baked-in assumptions:** Hostinger's template (BIOS GRUB on `/dev/sda`, ext4 root by label, cloud-init owning the network with DHCP off, so on another provider a switch can leave the box offline); x86_64; Cloudflare DNS for any public app; an interactive sudo prompt; one hard-coded `admin`; the host key as SOPS recipient.
- **Missing for on-budget:** PostgreSQL, backups, monitoring, log retention, unattended updates, CI deploys, TLS on the host (ACME DNS-01 for a tailnet-only name), disk encryption.
- **Correction:** the procedure's reconstruction says the locked nixpkgs has no Tailscale Serve option. It has `services.tailscale.serve`, in a separate `tailscale-serve.nix` (added 2026-01-21), but that module only applies a Tailscale Services configuration (`svc:<name>` entries) with `tailscale serve set-config --all`. A Tailscale Service needs a host with a tag identity, the service defined in the admin console first, and an admin's approval of the host unless auto-approval is set up ([Tailscale Services](https://tailscale.com/kb/1552/tailscale-services)). Node-level `tailscale serve`, the video's internal ingress, has no NixOS option that I found; it would take a unit that runs the CLI (judgment).

## Fit for on-budget

| Need | What the approach gives | Verdict |
|---|---|---|
| One source of truth that agents edit | The whole host in Git; unknown options fail at evaluation | **Keep** |
| Safe deploys | Built before activation, generations, no registry | **Keep**; add magic rollback, since SSH is tailnet-only |
| API, worker, web | Video: Nix packages as systemd units | **Keep**: hardened units, no containers |
| PostgreSQL, backups, monitoring, updates | Nothing in either | **Add** |
| HTTPS on the tailnet for the web app, API and callback; a public association file | Repo: tailnet mode closes every public port, as ADR 0003 requires, but serves no TLS; public apps go through Cloudflare Tunnel | **Keep** the tailnet mode; **add** Caddy with a DNS-01 certificate on `tailscale0` and the association file on static hosting |
| Confidential bank data | A tunnel decrypts at Cloudflare | **Change**: TLS ends on the VPS, no tunnel |
| Any EU provider | Hostinger template | **Change**: nixos-anywhere + disko |
| Unattended deploys, no Linux builder on the Mac | Local x86_64 build, `--no-check-sigs`, trusted `admin`, sudo prompt | **Change**: CI builds, deploy-rs, signed closures |
| Public repo, self-hosters (ADR 0001) | Personal settings sit next to the code | **Change**: public module + template, private ops repo |
| A third-party image (PowerSync, if adopted) | The video keeps Docker for these | `oci-containers` with `imageFile = dockerTools.pullImage { … }` (fetched at build time, digest-pinned), ports on 127.0.0.1 |

- **Hardened units over NixOS containers.** The NixOS manual calls containers "not perfectly isolated"; their forwarded traffic escapes the repo's firewall mode, and a private network needs NAT for egress (bank API, APNs). systemd gives each unit its own user, file-system view, network namespace and credentials. (**H**)
- **Agents and Nix** (**L**: no benchmark found, only anecdotes). The module system rejects undefined options at evaluation; `nix flake check`, nixfmt, statix, deadnix and VM tests catch the rest; mcp-nixos looks up real options. nixpkgs APIs churn (`pnpm.fetchDeps` became `fetchPnpmDeps`, fetcher versions went from 1 to 5 in a year, 26.05 removed the Bash `nixos-rebuild` and promtail), so agents trained on older code write deprecated patterns unless pointed at the pinned manual.
- **Data protection.** Under ADR 0001 the instance holds only its owner's households; whether GDPR's household exemption then applies wasn't researched. The argument against a TLS-terminating proxy holds either way: with TLS on an EU VPS, the VPS host is the only processor in the data path that can read it (Tailscale's DERP relays forward only WireGuard-encrypted packets; APNs payloads stay encrypted, per apple-client-stack.md).
- **The update loop survives the split.** The ops repo pins `on-budget` as an input, so `nix flake update on-budget` + `just deploy` is the video's loop, run weekly by CI.
- **Bank provider fit.** Enable Banking registers allowed `redirect_urls` per application and sends no webhooks for account information, so no third party connects in. The consent return is a navigation in the member's browser to the instance's https callback, not an inbound connection, so it works on the tailnet ([bank-aggregation.md](bank-aggregation.md) §4.5, ADR 0003); whether EB accepts a tailnet redirect URL is that note's spike 4. User-triggered fetches must forward the member's IP and user agent as PSU headers, so the proxy must pass the client IP: here a tailnet address, which banks may refuse (spike 1).

## Proposed target infrastructure

All of this section is judgment built on the sources above; code is sketch.

### Repositories and flake layout

```text
on-budget/  (public)                              on-budget-ops/  (private, made from the template)
├─ flake.nix   packages · nixosModules · checks   ├─ flake.nix   inputs: nixpkgs (nixos-26.11), on-budget
│              · templates · devShells            │              (follows nixpkgs), sops-nix, disko, deploy-rs
├─ nix/packages/{api,web}.nix   (lib.fileset)     ├─ justfile    install · deploy · deploy-here · rollback · ssh
├─ nix/modules/{app,backup,monitoring,base}.nix   ├─ hosts/prod/{default,settings,disko}.nix · facter.json
├─ nix/tests/{smoke,backup-restore,upgrade}.nix   ├─ secrets/prod.yaml (sops) · .sops.yaml
└─ nix/template/   the ops skeleton               └─ .github/workflows/{check,deploy,update}.yml
```

- `packages` for `x86_64-linux` and `aarch64-linux`; `lib.fileset` keeps app-only and Xcode changes from rebuilding the server.
- The public modules carry everything a self-hoster needs (`services.on-budget.*`); the ops repo adds only host facts, secrets and workflows.
- The template reuses the starter's good parts (settings file, auto-imported modules, sops bootstrap, SSH assertions); keep its MIT notice wherever code is copied.
- `follows` gives the server one nixpkgs; the ops CI re-runs on-budget's VM tests against it.

### Host

- **Machine:** one x86_64 KVM VPS in an EU data centre, ≥ 2 vCPU / 4 GB / 40 GB, IPv4 + IPv6. `just install` runs nixos-anywhere + disko: GPT with a BIOS-boot partition and an ESP so GRUB boots on either firmware, hardware facts from `nixos-facter`, and a host key generated beforehand and passed with `--extra-files`, so secrets decrypt on first boot.
- **OS:** `nixos-26.11` from its release; `system.stateVersion` set once at install; `time.timeZone = "UTC"`; weekly `nix.gc`, `boot.loader.grub.configurationLimit = 10`; journald capped at 30 days.
- **Accounts:** a human login (the starter's `admin`) with password sudo and a hardware-backed SSH key that needs a touch; a `deploy` account with passwordless sudo for CI. Both are root-equivalent. No Nix `trusted-users` beyond root: closures arrive signed, and the CI key's public half goes in `nix.settings.trusted-public-keys`. Root login stays off.
- **Network:** the public interface answers only Tailscale's UDP port, for direct connections. 443 (Caddy; TCP, and UDP for HTTP/3), 22 (SSH) and exporters are open only on `tailscale0` (`networking.firewall.interfaces.tailscale0`), rather than the starter's "trust all of `tailscale0`". On 26.05 `services.openssh.openFirewall` defaults to `true` and adds 22 to the global allow list, which a per-interface rule doesn't remove, so set it to `false`, as the starter's tailnet mode does with `mkForce`. sshd still listens on every interface (binding `services.openssh.listenAddresses` to the Tailscale address would make sshd depend on `tailscaled` at boot: judgment), so the firewall is the only gate: a VM test checks that 22 and 443 are closed on the public interface, and a provider firewall that admits only Tailscale's port adds a second layer (judgment). Tag the VPS `tag:prod` (tagged nodes don't expire); ACLs: `tag:ci` → `tag:prod:22`, the owner's devices → `tag:prod:22,443`, members' devices → `tag:prod:443`. Break-glass: the provider console plus the human account's password.

### Services: the `services.on-budget` module

- `on-budget-migrate`: a oneshot re-run whenever the package changes, ordered before the API and the worker. Expand/contract migrations only, because a generation rollback leaves the schema as it is.
- `on-budget-api`: socket-activated on `/run/on-budget/api.sock` (group `caddy`, mode 0660) with `PrivateNetwork=yes`; file-system Unix sockets still work, so Caddy reaches it and it reaches Postgres, but nothing else. It holds no aggregator key. Set `stopIfChanged = false`: when a switch changes the unit, switch-to-configuration then `systemctl restart`s it in one step and leaves the socket listening, so connections queue, and a failed start exits the switch with code 4, which deploy-rs's `autoRollback` reverts. With the default `stopIfChanged = true`, the socket is stopped before activation and started after it, refusing connections in between; `notSocketActivated = true` only adds an eager start. Readiness: `Type=notify` if the runtime can send `READY=1`, else an `ExecStartPost` probe of `/up`. A crash after readiness is caught only while the switch waits for systemd to settle, which its code calls "inherently a race condition". A changed `.socket` unit isn't restarted by a switch at all (the manual: "currently ignored"), so socket edits need a manual restart or a reboot.
- `on-budget-worker`: the only unit holding the aggregator key, the APNs `.p8`, the VAPID key and the token-encryption key. Egress only, plus a local Unix socket for the API's calls that need those keys: consent start, code exchange, and user-present refreshes carrying the member's IP and user agent. APNs uses Apple's 17.0.0.0/8 on 443 or 2197; Web Push endpoints vary, so IP allow-lists fit only a push-only unit.
- All three get the hardening below. `MemoryDenyWriteExecute` suits an AOT-compiled Swift binary, and Node only with the experimental `--jitless`, which disables "runtime allocation of executable memory" at a cost that "may be severe", without WebAssembly (so no built-in TypeScript stripping: ship compiled JavaScript); whether Node then runs under the setting is unverified. Bun JITs. NixOS `confinement` where it fits.
- PowerSync, if adopted, runs as an image loaded from the store, with ports on 127.0.0.1 only, because Docker's published ports bypass host firewall rules.

```nix
# Sketch; option names under services.on-budget are proposals
let hardening = {
  DynamicUser = true; ProtectSystem = "strict"; ProtectHome = true; PrivateTmp = true;
  PrivateDevices = true; NoNewPrivileges = true; CapabilityBoundingSet = ""; UMask = "0077";
  ProtectKernelTunables = true; ProtectKernelModules = true; ProtectControlGroups = true;
  SystemCallFilter = [ "@system-service" ]; Restart = "on-failure";
}; in {
  systemd.sockets.on-budget-api = {
    wantedBy = [ "sockets.target" ];
    listenStreams = [ "/run/on-budget/api.sock" ];
    socketConfig = { SocketGroup = "caddy"; SocketMode = "0660"; };
  };
  systemd.services.on-budget-api = {
    wantedBy = [ "multi-user.target" ]; stopIfChanged = false;   # restart in one step; the socket stays up
    requires = [ "on-budget-migrate.service" ];
    after = [ "on-budget-migrate.service" "postgresql.target" ];
    serviceConfig = hardening // {
      User = "on-budget-api";                          # Postgres peer auth maps it to a role
      ExecStart = "${cfg.package}/bin/on-budget serve";
      PrivateNetwork = true; RestrictAddressFamilies = [ "AF_UNIX" ];
      LoadCredential = [ "session-key:${cfg.sessionKeyFile}" ];
    };
  };
  systemd.services.on-budget-worker.serviceConfig = hardening // {
    User = "on-budget-worker"; ExecStart = "${cfg.package}/bin/on-budget worker";
    RestrictAddressFamilies = [ "AF_UNIX" "AF_INET" "AF_INET6" ];
    LoadCredential = [ "aggregator.pem:${cfg.aggregatorKeyFile}" "apns.p8:${cfg.apnsKeyFile}"
                       "vapid.pem:${cfg.vapidKeyFile}" "token-key:${cfg.tokenKeyFile}" ];
  };
}
```

### Secrets

- sops-nix with one YAML file per host. `.sops.yaml` lists three recipients: the owner's age key, an offline recovery key and the host key (through `ssh-to-age`). Replacing a host means adding the new key's recipient and running `sops updatekeys`.
- Secrets are decrypted at activation into `/run/secrets` (root, 0400) and handed to units with `LoadCredential`; the app reads `$CREDENTIALS_DIRECTORY`. Never put one in a Nix string: the store is world-readable.
- CI never decrypts. It holds only the deploy SSH key, the closure-signing key and the Tailscale OIDC client; VM tests pass dummy files to the same options.
- Inventory: aggregator, APNs, VAPID and token-encryption keys (worker); session key (API); the DNS API token for DNS-01 (lego); restic passwords, repository URLs and the Storage Box SSH key; Healthchecks ping URLs; the Tailscale auth key (install only).

### Ingress

ADR 0003 keeps the instance "reachable only over Tailscale", so Caddy (2.11.7 in 26.05) serves one origin, `app.<rp-id>`, on the tailnet ([web-client-sync.md](web-client-sync.md) §5.3), and the RP ID host stays a public static site:

```nix
# Sketch: a DNS-01 certificate through lego, since no CA can reach the host
security.acme = { acceptTerms = true; defaults.email = "…"; };
security.acme.certs."app.example.org" = {

  environmentFile = config.sops.secrets.acme-dns.path;      # an API token scoped to the zone
};
services.caddy.virtualHosts."app.example.org".useACMEHost = "app.example.org";  # reloads Caddy on renewal
networking.firewall.interfaces.tailscale0 = { allowedTCPPorts = [ 443 ]; allowedUDPPorts = [ 443 ]; };
# services.caddy.openFirewall stays false, its default: nothing opens on the public interface
```

```caddy

  admin unix//run/caddy/admin.sock   # instead of localhost:2019, which any local process can reach

}

```

- One origin for the SPA, `/api`, the SSE stream and the bank callback (web-client-sync.md §5.1), with that note's CSP and headers. Hashed assets get `immutable`; `index.html` and the service worker get `no-cache`. Off the tailnet, the web app behaves as offline (§5.3).
- **Certificate.** lego through `security.acme` covers the DNS host's API without a custom Caddy build, and the Caddy module points `useACMEHost` vhosts at the certificate and reloads Caddy after renewals. The alternative is a Caddy built with the provider's caddy-dns module (`caddy.withPlugins`). The DNS token can rewrite the zone, so scope it to the zone or to a delegated `_acme-challenge` name (judgment).
- **Client IP.** Caddy passes it (`X-Forwarded-For`) for the PSU headers; on the tailnet it is the device's 100.64.0.0/10 address, which banks may refuse ([bank-aggregation.md](bank-aggregation.md) spike 1). Rate limits live in the app (sign-in, invites, bank links); pick nginx instead to get proxy-level `limit_req` without an unofficial plugin.
- **DNS.** `app.<rp-id>`: A and AAAA to the Tailscale addresses, in public DNS or Tailscale split DNS (whether every network resolves such answers is unverified, per web-client-sync.md). The RP ID: the static host serving the association file (web-client-sync.md open question 4). CAA `0 issue "letsencrypt.org"`, plus the static host's CA if it differs. Cloudflare, if used, stays DNS-only.
- **Patching.** 2.11.8 (2026-11-04) and 2.11.9 (11-05) are security releases; among their fixes, the `file` matcher behind `try_files` resolved `/file/./` to the file ([GHSA-25cw-38mq-q7m6](https://github.com/caddyserver/caddy/security/advisories/GHSA-25cw-38mq-q7m6)), and `reverse_proxy` passed hop-by-hop headers in 1xx responses ([GHSA-8qx7-j2v2-x6q5](https://github.com/caddyserver/caddy/security/advisories/GHSA-8qx7-j2v2-x6q5)). Master has 2.11.9 (#583576, merged 2026-11-06), so 26.11 should ship it; its automatic 26.05 backport failed, so track it while on 26.05.
- **Public variant, only after an ADR amending 0003 and `PRODUCT.md`.** What could justify it: browsers that can't run Tailscale, such as work PCs (web-client-sync.md §5.3); banks refusing a tailnet `Psu-Ip-Address`, or Enable Banking a tailnet redirect URL (bank-aggregation.md spikes 1 and 4); external TestFlight or App Store review, which needs a reachable backend (apple-client-stack.md §4.4; [native-apps-auth.md](native-apps-auth.md) keeps to the internal TestFlight group, which needs none). The bank callback alone doesn't: the redirect is a browser navigation, not an inbound connection. What it changes: 80/443 public through `services.caddy.openFirewall` with HTTP-01 or TLS-ALPN (no geo-blocking), the association file can move onto Caddy, an internet probe, Caddy patched within days, and web-client-sync.md §5.3 item 5's hardening (passkey-only login, invite-only enrollment, auth rate limits). Cloudflare Tunnel stays out either way, since it terminates TLS at Cloudflare.

### Database and backups

- `services.postgresql`: `package = pkgs.postgresql_18`; `settings.listen_addresses = lib.mkForce ""` (socket only; the module sets `localhost` without `mkDefault`); `ensureDatabases` and `ensureUsers` for `on-budget` (the owner role, used by migrations), `on-budget-api` and `on-budget-worker`, with grants that let only the worker read aggregator tokens. Major upgrades only on purpose, rehearsed in a VM test first.
- **Backups, sized by ADR 0001:** an hourly `pg_dump` streamed into restic (`command`), uncompressed so restic deduplicates, to two EU repositories: a Hetzner Storage Box (SFTP, €3.20, snapshots) and a second provider with append-only mode or object lock. Retention such as 48 hourly, 35 daily and 12 monthly snapshots, stated in the privacy notice. That gives an RPO of at most one hour without WAL archiving's failure mode: a failing archive command fills `pg_wal` until PostgreSQL PANICs.
- **Restores and offline-first clients** (judgment; [sync-engine.md](sync-engine.md) leaves "Backup and restore semantics" open, question 7). A restored dump rewinds the sync counter, the change log and each client's `last_mutation_id` by up to the RPO, while clients hold later cursors and have dropped mutations the server had acknowledged. Unwarned, they would skip new rows that reuse sync IDs they've seen, and the lost window's edits would vanish. So each restore writes a new restore epoch, returned by bootstrap and pull. A client that sees a new epoch keeps its outbox, re-pushes the acknowledged mutations it still holds above the server's `lastMutationId` for it (the idempotent push skips the rest), then re-bootstraps; clients must therefore keep acknowledged mutations for longer than the RPO. The worker's fetch ledger rewinds too, so after a restore it counts every account's background quota as spent for the lost window, then re-fetches with its usual overlap.
- **Drills:** a monthly timer restores the latest dump into a scratch database, runs invariant queries, drops it and pings Healthchecks with the duration. A quarterly rebuild on a throwaway VPS (`just install`, restore, smoke test) measures the RTO. A CI VM test runs backup, wipe and restore, then reconnects a client that wrote after the dump and checks that its edits come back.
- **Point-in-time recovery later, if the RPO must be minutes:** pgBackRest needs an overlay to ≥ 2.59.3, its cipher pass through `PGBACKREST_*` variables (the module disables `cipher-pass`), and on 26.05 the SFTP-key fix (#556686). WAL-G has no module. Either needs archiver and disk alerts.

### Jobs

- **The worker owns the bank schedule:** a 15-minute loop picks due accounts from a database ledger capped per account and endpoint over a trailing 24 h (start at 3, never above 4; catch-ups and retries count). Alerts are evaluated after each sync, plus an hourly pace sweep and a daily consent-expiry check. On-demand syncs from the API need a running worker anyway, and self-hosters on other platforms shouldn't depend on systemd timers. The alternative is a `Persistent` timer with `RandomizedDelaySec` that starts a oneshot dispatcher.
- **systemd timers run the host jobs:** hourly backup, weekly `restic check`, monthly restore drill, the 5-minute heartbeat, weekly `nix.gc`, and a nightly `reboot-if-needed`, which reboots only when `/run/booted-system` and `/run/current-system` differ in kernel, initrd or modules.

### Monitoring and logs

- **Healthchecks.io** (run from Riga, hosted on Hetzner; 20 checks free): the heartbeat (a down VPS shows as missing pings), the worker's cycle, each backup repository and the restore drill. Every unit's `OnFailure=` pings a "failed units" check.
- **Heartbeat script:** `systemctl is-system-running`, disk below 80 %, `app.<rp-id>`'s certificate valid for more than 14 days, the association file served on the RP ID host, `pg_isready`, and `/up` through `app.<rp-id>` (DNS, certificate, Caddy and API in one request).
- **Logs:** journald for 30 days. Never log transaction payloads, tokens or bank identifiers. Caddy access logs off, or kept briefly.
- **Optional:** node and postgres exporters on `tailscale0`, scraped by VictoriaMetrics or Prometheus on another tailnet node; an HTTPS probe with Gatus or Uptime Kuma, also from another tailnet node, since no internet probe can reach the instance. 26.05 has modules for all of them.

### CI/CD and the deploy flow

1. **Public repo, every PR and `main`:** `ubuntu-latest` (4 vCPU / 16 GB, free, KVM) with `cachix/install-nix-action`, then `nix flake check -L`: packages, unit tests, nixfmt/statix/deadnix, and `testers.runNixOSTest` VM tests (Postgres + migrate + API + worker against a mock aggregator + Caddy with an internal CA; backup and restore; upgrade from the previous release). Dependabot `nix` bumps its `flake.lock`.
2. **Ops repo, PR:** evaluate and build `nixosConfigurations.prod.config.system.build.toplevel`, run deploy-rs `deployChecks`, and a host VM test (the prod configuration with dummy secrets and an internal CA).
3. **Ops repo, push to `main` or manual dispatch:** the checks again, then a `deploy` job (`needs: check`; environment `production` limited to `main`). On GitHub Free a private repo has neither environment secrets nor deployment-branch rules, so the ops repo needs GitHub Pro; otherwise the root-equivalent deploy key would be a repository secret, readable by a workflow on any branch an agent pushes. Required reviewers stay public-only even on Pro. It joins the tailnet with `tailscale/github-action@v4` over OIDC as an ephemeral `tag:ci` node, runs `just deploy` (deploy-rs builds on the runner, signs with `LOCAL_KEY`, copies, activates, confirms), then a smoke test (`/up`, `systemctl --failed`).
4. **Weekly update:** either Dependabot `nix` opens the lock PRs and the merge deploys (its "private repositories" limit concerns private flake inputs, and every input here, on-budget included, is public), or a scheduled job runs `nix flake update` and the checks, then commits and deploys, keeping the loop in one workflow. update-flake-lock also gives a PR flow, but needs a PAT or app token to trigger CI.
5. **Twice a year:** move `nixos-26.11` to `nixos-27.05` in `flake.nix`, fix deprecations, run the VM tests, deploy and reboot well before the old release's end of life. Since dependabot-core #14710, Dependabot proposes that bump itself once the new branch exists, likely around branch-off and before the release, although GitHub Docs say it doesn't touch `flake.nix`: review that PR on purpose instead of merging it with the weekly ones.
6. **Emergencies, from a Mac:** `just deploy-here` evaluates locally and builds on the VPS; `just rollback` switches to the previous generation. Then delete the abandoned generation: deploy-rs reverts with `nix-env --rollback`, which picks the highest generation below the current one, so after a manual rollback its next revert would land on the abandoned one (judgment, from activate.rs).

```just
# Sketch of the ops justfile. CI: build on the runner, sign, copy, activate, confirm (checks already ran)
deploy:
    deploy .#prod --skip-checks
# from a Mac without a Linux builder: build on the VPS
deploy-here:
    deploy .#prod --remote-build
rollback:
    ssh -t admin@prod 'sudo nixos-rebuild switch --rollback'
# new or replacement VPS (wipes its disk): host key → .sops.yaml → sops updatekeys → nixos-anywhere --extra-files
install ip:
    ./scripts/install.sh prod {{ip}}
```

### Staging

- **App changes:** the instance's test household, with synthetic data (`PRODUCT.md`).
- **Infra changes:** the host VM test on every ops PR; a throwaway, hourly-billed VPS for provider-specific work (install, disk layout, networking) and the quarterly rebuild drill. No permanent staging VPS while an instance serves one owner's households.

### Local development

- `nix develop` on macOS and Linux with the backend toolchain, just, sops, age, ssh-to-age and deploy-rs; PostgreSQL 18 through services-flake + process-compose or devenv's `services.postgres` (Unix socket, no Docker). The Apple apps stay in Xcode.
- VM tests and Linux builds run in CI. Locally they need a Linux builder: Determinate's native builder, `darwin.linux-builder`, or `linux-builder-vz` from 26.11.
- **Deploy-machine Nix:** a release fixed for the 2026 advisories (≥ 2.35.3 or 2.34.9, or a patched Lix or Determinate) with flakes, and `ca-derivations` and `recursive-nix` off. The old scripted multi-user installer can leave the store's contents user-owned (GHSA-hf6w-2rg9-v84g). If `find /nix/store -mindepth 1 ! -user root | head` prints anything, the advisory's fix is to upgrade and garbage-collect, which "typically" deletes the bootstrap closure, or to run its `chown -h 0:0` loop over that same `find`. `nix store verify --all` then checks every path against the hashes in the Nix database. Reinstalling (`nix-installer … install --enable-flakes`, Lix or Determinate) is optional, for when tampering can't be ruled out.
- **Agent rules for both repos' `AGENTS.md`:** use the pinned channel's manual and mcp-nixos, not memory (`pkgs.nixosTest`, `pnpm.fetchDeps`, Bash-`nixos-rebuild` flags and promtail are gone); run `nix flake check` before every PR; add a VM test for every module change, and for SSH, firewall or Tailscale edits one that logs in over the new path and finds the public interface still closed; keep secrets out of Nix strings; never change `stateVersion`; never deploy around CI.

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| Lockout after an SSH, firewall, Tailscale or network edit | Magic rollback (raise `confirmTimeout` to 60–120 s and test it in S1). It can't revert a deploy whose previous generation wasn't deployed by deploy-rs, such as one from nixos-anywhere or a break-glass `nixos-rebuild` build ([#86](https://github.com/serokell/deploy-rs/issues/86)), so follow `just install` or any such switch with a harmless deploy-rs deploy; a VM test that logs in over the new path; tagged node, so no key expiry; provider console + password |
| CI's deploy credential is root | Private ops repo on GitHub Pro, for environment secrets limited to `main`; OIDC, ephemeral `tag:ci`, ACL to port 22 only; separate signing and SSH keys, rotated; hardware-backed owner keys |
| A port left open on the public interface | `services.openssh.openFirewall = false`; only Tailscale's UDP port in the global allow list; a VM test that probes 22 and 443 there; a provider firewall as a second layer |
| Agents write wrong or deprecated Nix | Evaluation errors, `nix flake check`, VM tests, the pinned manual + mcp-nixos; read infra diffs yourself |
| Two OS upgrades a year, each in a one-month window | Start at branch-off; VM tests; deploy and reboot well before 12-31 and 06-30 |
| nixpkgs lag (pgBackRest 2.58, Swift 6 only from 26.11) | restic dumps don't depend on pgBackRest; hash-pinned overlays; Swift on 26.11 or the Static Linux SDK |
| Public 80/443 with no CDN in front (public variant only) | Only Caddy listens, patched promptly (2.11.8 and 2.11.9 were security releases); passkeys + invites; app rate limits; HSTS; provider DDoS protection (free at Hetzner) |
| One VPS is a single point of failure | Offline-first clients keep working, alerts arrive late; hourly dumps; a measured quarterly rebuild |
| A compromised host wipes the backups | A second provider with append-only mode or object lock; Storage Box snapshots (check an SFTP key can't delete them); one password per repository |
| Disk full (logs, generations, WAL) | journald caps, `nix.gc`, `configurationLimit`, the heartbeat's disk check; no WAL archiving until it's monitored |
| Missed certificate renewals (45-day certificates by 2028) | lego renews over DNS-01 and reloads Caddy; an expired or revoked DNS token stops renewals, so the heartbeat checks expiry; in the public variant, no geo-blocking |
| Downtime during deploys | Socket activation with `stopIfChanged = false`, so the socket keeps queueing while the API restarts; `lb_try_duration` for reboots; expand/contract migrations |
| A restore rewinds sync state | A restore epoch; clients keep acknowledged mutations longer than the RPO and re-push them; the worker treats the lost window's fetch quota as spent; drills with a reconnecting client |
| Reboots for kernel updates | Nightly `reboot-if-needed`; the console and GRUB menu as fallback; systemd-boot boot counting on UEFI hosts from 26.11 |
| A compromised Mac (agents run shells there) | Production deploys from CI; owner SSH and age keys need a touch; no trusted Nix users on the VPS |
| Provider capacity (Hetzner's restrictions) | nixos-anywhere works on any KVM VPS; test kexec on a throwaway first |

## Open questions and spikes

**For the owner**

1. Access: tailnet-only, as ADR 0003 decides, or public 80/443? Reopening it takes an ADR amending 0003 and `PRODUCT.md`; the triggers would be members' browsers that can't run Tailscale, bank-aggregation.md spike 1 or 4 failing on tailnet addresses, or external TestFlight review.
2. Provider: Hetzner (if it accepts new servers), OVHcloud, or Hostinger's ready template (KVM 2, in France, Germany or Lithuania)? x86_64 in every case.
3. Registrar and DNS host for the domain: an API that lego supports, ideally with zone-scoped tokens, for DNS-01; CAA support; Cloudflare in DNS-only mode is fine. And a static host for the association file.
4. Backend language: TypeScript packages cleanly on 26.05; Swift needs 26.11 or the Static Linux SDK. Swift keeps `MemoryDenyWriteExecute` at no cost, Node only with the experimental, much slower `--jitless`.
5. Is an RPO of one hour (hourly dumps) enough, or is point-in-time recovery worth the pgBackRest or WAL-G work?
6. CI deploys from the first backend release (GitHub Pro for environment secrets and the `main`-only rule in the private ops repo), or `just deploy-here` until then?
7. Full-disk encryption: worth an initrd SSH unlock on every reboot, which breaks unattended kernel reboots?
8. Self-hosters: the NixOS module and template only, or also an OCI image built by the same flake (`dockerTools.streamLayeredImage`)?
9. Write the ADR that records this design within 0003 (deploy-rs from CI, DNS-01 on the tailnet, restic backups) and supersedes the Kamal plan.

**Spikes**

- **S1 Install and deploy (1 day; on 26.05 now, or the 26.11 branch after 2026-11-23):** template → private ops repo; nixos-anywhere + disko on a throwaway VPS at the chosen provider (kexec, IPv6, console); sops with a pre-generated host key; deploy-rs over Tailscale with signed closures, and `--remote-build` as the untrusted `deploy` user; a harmless deploy-rs deploy first (the installed generation has no `deploy-rs-activate`), then break SSH on purpose and watch the rollback, including a deploy that restarts `tailscaled`; a DNS-01 certificate through lego and `useACMEHost`, Caddy's admin socket and reloads; 22 and 443 closed on the public interface; a reboot.
- **S2 CI (½ day):** a timed `runNixOSTest` (Postgres, a stub API, Caddy, backup and restore) on `ubuntu-latest`; an ops deploy through OIDC as `tag:ci`; `ls /dev/kvm` on `ubuntu-24.04-arm` if ARM ever matters.
- **S3 Backups (½ day):** restic to the Storage Box and a second EU target; restore time; whether a leaked SFTP key can delete snapshots; object lock on the second target.
- **S4 Point-in-time recovery (optional, 1 day):** pgBackRest ≥ 2.59.3 through an overlay against WAL-G with a small module, both to the Storage Box; archiver and disk alerts.
- **S5 Packaging (once the backend is chosen):** `fetchPnpmDeps` or bun2nix against Swift 6.4 on 26.11; socket activation and readiness in that runtime; with Node, whether `--jitless` runs under `MemoryDenyWriteExecute` and what it costs.

**Not verified**

- Dependabot `nix` in practice: its `flake.nix` bumps (#14710) and its runs in a private repo with public inputs, both of which GitHub Docs contradict; test on the ops repo. Hetzner's IPv4 inclusion; OVHcloud's commitment terms, data centres, IPv6 and kexec; Hostinger's price without the 24-month prepay, and hPanel after a reinstall; Scaleway (blocked fetching) and netcup figures; Cachix and FlakeHub prices; GitHub Pro's current price (github.com/pricing no longer lists it).
- KVM on GitHub arm64 runners and the nspawn backend's daemon settings there; how Determinate's builder runs x86_64 and `determinate-nixd`'s licence; Rosetta for Linux VMs after macOS 27.
- Magic rollback when activation restarts `tailscaled` or `sshd`; Caddy's admin API on a Unix socket with NixOS reloads; Node `--jitless` under `MemoryDenyWriteExecute`.
- Swift 6.4 and Caddy 2.11.9 in 26.11 final, and the 26.11 date itself; deploy downtime in practice.
- Whether banks accept a tailnet `Psu-Ip-Address` and Enable Banking a tailnet redirect URL (bank-aggregation.md spikes 1 and 4); whether public A/AAAA records to Tailscale addresses resolve on every network (web-client-sync.md).
- LUKS with remote unlock; hosting requirements an aggregator might impose; the status of the CJEU appeal on the EU-US DPF (C-703/25 P).
- The video was not watched: captions, description and repo only.
