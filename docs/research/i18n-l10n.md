## Question

How should on-budget localize (English and French now, more languages later, no right-to-left) and regionalize (any European country: date and time formats, 12/24-hour clock, time zones, currencies, number formats) consistently across the Apple apps, the web app and the backend? Which rules does every codebase follow, and with which tools?

## TL;DR

1. **Strings: one ICU MessageFormat catalog in git, generated for every target.** `l10n/messages/{en,fr}.json` holds a restricted ICU MessageFormat 1 subset, with English as the source and French required in the same PR. A small in-repo generator emits typed TypeScript over FormatJS for the shared UI (iPhone, Mac and web), and for the server if the server is TypeScript. For the native Swift parts (the watch app, widgets, the notification service extension), it emits Apple String Catalogs (`.xcstrings`) plus typed Swift accessors in a package. Strings that iOS reads from a bundle go into the target that owns them: each target's Info.plist strings and the app's push-fallback keys. Agents edit two JSON files. CI checks syntax, placeholders, plural coverage, French typography and length budgets, and runs `formatjs verify` on the JSON and, in its Apple mode, on the generated catalogs. There is no translation platform in v1; Tolgee comes later if outside translators join. **M** (tool facts H; the generator is a judgment.)
2. **Regional settings are user data, not "whatever the system locale says".** Store the region, the hour cycle and the first day of the week, each defaulting to "auto"; an explicit value wins on every device. Language works differently. On Apple it follows the OS per-app language setting, which Apple says not to override in code, so the shared UI on iPhone and Mac uses the bundle's resolved localization, like the watch app and the widgets. The synced language drives only the web app and email. Swift renders one composite `Locale` such as `fr-FR-u-rg-dezzzz-hc-h23`, which is Apple's own region-override model. Browsers and Node ignore `rg` when formatting, and browsers don't expose OS overrides (Edge and Firefox do only when the OS and browser languages match). Every JavaScript surface, iPhone and Mac included, therefore builds two `Intl` locales: words follow the UI language, while numbers and numeric dates follow the region. Measured: this matches Apple's output for en-US UI with region FR or DE, fr UI with region DE and de UI with region FR; fr-CH (Chrome currency) and en UI with region PT still differ. A browser can't resolve "auto" by itself: on a Mac set to English (US) with region France and a 24-hour clock, Safari's WebKit reports only `en-US` and prints `-€1,234.50`, `11/7/2026` and `7:05 PM` (measured). So on the web, the Expo stack's first Mac client included, "auto" takes the settings the user's Apple apps last reported, or else a choice made once at first run. **M-H**
3. **Inputs follow the profile too.** A native `<input type=date|time>` follows the browser, not the page or the profile: on that Mac, WebKit shows `07:05 PM` and `11/07/2026` even inside `lang="fr-FR"`, while Chrome shows `19:05` (measured). On the Expo stack, the web build uses React Aria's date and time fields with an explicit `hourCycle` and `firstDayOfWeek`. The iPhone uses Expo UI's SwiftUI `DatePicker` with the resolver's Apple locale: on macOS, a SwiftUI picker honours `hours=h23;fw=mon` in that locale alone (measured; iOS unverified, spike L2). One `AmountInput` accepts `,` or `.` and parses exactly to minor units. **M**
4. **CLDR output differs across engines (measured), and now within one device.** The same input produces different strings for `fr-CH` euros, `en-FR`, HUF decimals, U+202F vs U+0020, and for locales that Chrome lacks (Icelandic, Maltese, Luxembourgish, Irish, Basque, Albanian, Macedonian), which fall back to en-US. With one shared UI, the iPhone app's JavaScript engine and its own watch app and widgets (Foundation) can disagree in exactly these cases. If the shared UI is React Native, Hermes's iOS `Intl` has only `Collator`, `NumberFormat` (no `roundingMode`, `signDisplay`, compact notation or `formatToParts`) and `DateTimeFormat` (whose `formatToParts` splits the formatted string, a method its maintainers call broken), and no `PluralRules`, `RelativeTimeFormat`, `ListFormat`, `Locale`, `Segmenter` or Temporal. FormatJS polyfills then become mandatory in the iPhone app (and in the iPad app on the Mac), not only on some browsers. With en and fr data and every time zone they come to about 3.7 MB of unminified JavaScript (measured file sizes; start-up cost not measured). The rules are: field-based formats instead of presets, explicit fraction digits and rounding, a locale allowlist with polyfills, and cross-platform tests that normalize whitespace. **H** (Hermes facts from its docs and source, not measured: **M**.)
5. **Time: instants are UTC; bank dates and budget periods are civil dates; the household's IANA zone defines "today".** Periods are calendar months. Convert local times to instants only in app code, with Temporal's `compatible` policy, because PostgreSQL resolves fall-back overlaps the other way. Temporal ships in Chrome 144+, Firefox 139+, Node 26, Deno 2.7 and Bun 1.4. Safari 27.3 beta (2026-11-03) adds it, but the released Safari and iOS 27.2 lack it, and so does Hermes. The shared UI therefore loads `temporal-polyfill` 1.0.8 whenever `globalThis.Temporal` is missing. That polyfill reads every zone offset from `Intl.DateTimeFormat.formatToParts`, so on Hermes it must load after FormatJS's `DateTimeFormat` and its full time-zone data, which freezes the zone rules at build time. The polyfill lists only browsers and Node as supported, so this pairing is untested (spike L4). **H** (the Hermes path: **M-L**)
6. **Money: Int64 minor units plus the ISO 4217 code**, as [sync-engine.md](sync-engine.md) already says. Exponents come from a pinned ISO 4217 table and display digits from a pinned CLDR table, and every formatter call sets its rounding. Defaults differ: Apple rounds half-even and Intl half-expand, so one HUF amount prints three different ways. **H**
7. **Europe in 2026:** the euro is the currency of 21 of 27 EU states since Bulgaria joined on 2026-01-01, and BGN has been withdrawn from ISO 4217. Six EU states keep their own currency, and the ECB's June 2026 report finds none of the five assessed ready to adopt the euro. **H**
8. **Mixed currencies:** each household has one base currency. A foreign-currency account converts at the bank's applied rate or at the ECB reference rate of the booking date, and the result is stored with the rate exactly as published, its source and its date, and never recomputed. The ECB publishes 29 currencies "for information purposes only". Card spending abroad from a euro account needs no FX, because the bank books it in euros. **M**
9. **Backend:** store codes (BCP 47, ISO 3166, ISO 4217, IANA), never formatted text. Push text is rendered on the device by the notification service extension, and emails on the server from the same catalog, with language tracked per device. Diacritic-insensitive search uses one shared `searchKey()` spec, SQLite FTS5 where the client's SQLite has it, and PostgreSQL 18's `und-u-ks-level1` ICU collation. **M-H**

**Takeaways (H).**
- **Field-based formats agree.** With field options (`{year, month, day}`, `{year, month: short, day}`, `{hour, minute}`) and EUR forced to 2 digits, Apple, the Safari engine and Chrome produced identical strings for 19 of 25 European locales. The six differences were `fr-CH`, `cs-CZ`, `bg-BG`, `el-GR`, `en-FR` and `fr-DE`: whitespace characters, an AM/PM marker, and composite or regional data.
- **Presets don't.** The `de-DE` short date is `07.11.26` in Chrome (`dateStyle: 'short'`), while Apple's `.numeric` style gives `7.11.2026`.
- **Engines patch ICU output.** Browsers deliberately replace U+202F with U+0020 in date output for web compatibility after CLDR 42. See the [WPT test](https://github.com/web-platform-tests/wpt/pull/41760), the [Node/V8 patch](https://github.com/nodejs/node/commit/c786ed3ecc) and [Firefox](https://bugzilla.mozilla.org/show_bug.cgi?id=1792775). Apple's ICU carries Apple customizations ([swift-foundation-icu README](https://github.com/swiftlang/swift-foundation-icu)).
- **Currency digits are implementation-defined.** ECMA-402 now says `CurrencyDigits` is "implementation-defined" and returns 2 only when nothing is known ([ECMA-402 draft, 2026-10-23, §16.5.1](https://tc39.es/ecma402/)). So engines legitimately disagree on HUF and the other cases above.

## 2. Strings

### 2.1 Apple platforms

- **Scope under ADR 0002.** Swift renders only the watch app and the extensions (widgets, the notification service extension, App Intents if any). The iPhone and Mac screens belong to the shared UI and take their strings from the TypeScript output (§2.2). iOS still reads some strings from each bundle itself: Info.plist usage descriptions and push-fallback keys (below).
- **String Catalogs.** A String Catalog (`.xcstrings`, a JSON file) collects strings that Xcode extracts on every build, with plural variants and "Vary by Device" variants such as Apple Watch ([Apple](https://developer.apple.com/documentation/xcode/localizing-and-varying-text-with-a-string-catalog)).
- **Xcode 26** ([release notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-26-release-notes)) added:
  - type-safe Swift symbols for *manually-managed* strings, behind "Generate String Catalog Symbols";
  - named format specifiers such as `%(landmarkCount)lld`;
  - comments generated by the on-device model;
  - key refactoring;
  - the `#bundle` macro.
- **Xcode 27** ([release notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-27-release-notes)):
  - Agents can translate String Catalogs, with "MCP tools to read, plan, and edit translations", a Generate Translations button and per-language style guides.
  - A source comment of "do not translate" marks a string Don't Translate in the catalog and `translate="no"` in XLIFF.
  - Machine translations carry `state-qualifier="leveraged-mt"` in exported XLIFF.
  - Previews can render another localization.
- **Packages.** A package declares `defaultLocalization` and reads its resources through `Bundle.module` ([Apple](https://developer.apple.com/documentation/xcode/localizing-package-resources)). SwiftPM has supported String Catalog symbol generation since 2025-06-25 ([#8815](https://github.com/swiftlang/swift-package-manager/pull/8815)). Strings that the system reads can't live in a package: APNs reads the app bundle's own table (Push, below), and Info.plist strings belong to the target that owns the Info.plist.
- **Linux servers (M).** Compiling a catalog runs Xcode's `xcstringstool`. A non-Apple build once failed on that step ([SwiftPM #9423](https://github.com/swiftlang/swift-package-manager/issues/9423), Windows, `swiftbuild` backend). [swift-build #973](https://github.com/swiftlang/swift-build/pull/973) closed it as completed on 2025-12-12 by moving Apple build rules "under the darwin domain", so that they aren't applied "when targeting a non-Apple platform". Linux builds now skip the catalogs instead of failing, so a Linux Swift server still gets no String Catalog at runtime (inference).
- **Choosing the language.** Since iOS 13, people can set a language per app in Settings ([WWDC19 403](https://developer.apple.com/videos/play/wwdc2019/403/)). Apple's guidance:
  - "do not attempt to set the application language manually in code";
  - for an in-app switch, "Launch into Settings";
  - the app then relaunches in the chosen language.
  
  The same talk adds two points. The setting "appears from [for] Multilingual Users" (transcript), so someone with a single preferred language may find no Language row; check this on iOS 27 (spike L3). And "the setting will also sync to the accompanying watch application". A shared JavaScript UI must still declare its languages to iOS for the setting to exist; Expo does this with `supportedLocales`, "used to enable per-app language selection in the system settings" ([Expo](https://docs.expo.dev/versions/latest/sdk/localization/)). macOS sets per-app languages under Language & Region > Applications ([Apple](https://support.apple.com/guide/mac-help/mh26684/mac)). The Watch's language is set from the Watch app on iPhone, with a term of address (feminine, masculine, neutral) for gendered languages ([Apple](https://support.apple.com/guide/watch/change-language-and-orientation-apd0bf18f46b/watchos)).

  For ranked preferences, iOS, watchOS and macOS 26 add `Locale.preferredLocales`, "taking into account any per-app language overrides" ([doc](https://developer.apple.com/documentation/foundation/locale/preferredlocales)), and Apple says "Locale.preferredLanguages may be deprecated in the future" ([WWDC25 222](https://developer.apple.com/videos/play/wwdc2025/222/)).
- **Grammar.** Automatic grammar agreement (`^[…](inflect: true)`) and [`TermOfAddress`](https://developer.apple.com/documentation/foundation/termofaddress) apply gender and number agreement ([`InflectionRule`](https://developer.apple.com/documentation/foundation/inflectionrule)). German and European Portuguese were added in 2023 ([WWDC23 10153](https://developer.apple.com/videos/play/wwdc2023/10153/)). Measured on macOS 26.6.2, `InflectionRule.canInflect` is true for fr, de, it and nl and false for pl. JavaScript has no equivalent, and most screens are JavaScript under ADR 0002, so copy must not rely on it (judgment).
- **Plurals.** For English, "`zero` is optional", and "if you provide a rule for a category that a language doesn't use, the system ignores it" ([Apple](https://developer.apple.com/documentation/xcode/localizing-strings-that-contain-plurals)). Yet the same page's English example "returns No homes found for 0". Measured on macOS 26.6.2 with a `.stringsdict`: a `zero` variant is used for 0 in English and in French, where 0 is otherwise `one`. In Latvian, whose CLDR `zero` category also covers 10 and 11–19, it is used for those numbers too. So ICU `=0` can map to Apple's `zero` variation in languages without a CLDR `zero` category (§2.3).
- **Pseudolanguages.** They appear "at the bottom of the App Language pop-up menu" in Scheme > Run > Options ([Apple](https://developer.apple.com/documentation/xcode/preparing-your-interface-for-localization)).
- **Push.** APNs can localize on the device with `loc-key`/`loc-args` (string arguments replacing `%@`), looked up in "the Localizable.strings file of your app bundle". Putting localized text in the payload "requires you to track the user's preferred language on your provider server" ([Apple](https://developer.apple.com/documentation/usernotifications/generating-a-remote-notification)).

Under ADR 0002 this library runs the iPhone, Mac and web screens, so the shared UI's JavaScript engine matters:
- **React Native (Hermes).**
  - Hermes's docs say `Intl` is "Not supported": in a default build "`Intl` is `undefined`", and even where it is enabled, `RelativeTimeFormat`, `PluralRules` and `formatRange` "are missing or partial". Their advice: "Use a polyfill such as FormatJS instead, accepting its start-up cost" ([Features.md](https://github.com/facebook/hermes/blob/static_h/doc/Features.md), rewritten 2026-10-30).
  - Hermes's Apple build script turns the partial Foundation-based `Intl` on (`-DHERMES_ENABLE_INTL:BOOLEAN=true`, [script](https://github.com/facebook/hermes/blob/static_h/utils/build-apple-framework.sh)). It covers `Collator`, `NumberFormat` and `DateTimeFormat`; on iOS, `NumberFormat` has no compact notation, `signDisplay` or `formatToParts` ([IntlAPIs.md](https://github.com/facebook/hermes/blob/static_h/doc/IntlAPIs.md)), and its `NSNumberFormatter`-based code reads no `roundingMode` ([source](https://github.com/facebook/hermes/blob/static_h/lib/Platform/Intl/PlatformIntlApple.mm)).
  - i18next agrees: "the Hermes engine still does not implement Intl.PluralRules" ([docs](https://www.i18next.com/translation-function/plurals)). Hermes's VM registers only `Collator`, `DateTimeFormat`, `NumberFormat` and `getCanonicalLocales` ([Intl.cpp](https://github.com/facebook/hermes/blob/static_h/lib/VM/JSLib/Intl.cpp)).
  - Two secondary sources say otherwise. Expo's guide says that with Hermes "you can use the Intl API on all platforms" ([Expo](https://docs.expo.dev/guides/localization/)). FormatJS's React Native guide marks `PluralRules` and `Locale` as supported by Hermes, with polyfills only "for older Hermes", and recommends each package's `shouldPolyfill` check ([guide](https://formatjs.github.io/docs/guides/react-native-hermes)). The engine's docs and source contradict both, so trust a runtime check over any table (judgment).
  - So load the FormatJS polyfills in the order FormatJS gives for React Native on iOS: `getCanonicalLocales`, `Locale`, `PluralRules`, `NumberFormat`, `DateTimeFormat` ([runtime requirements](https://formatjs.github.io/docs/guides/runtime-requirements)), then `RelativeTimeFormat` and `ListFormat`, which the resolver also uses. Use the `polyfill-force` entry points where Hermes has a partial implementation ([intl-numberformat](https://formatjs.github.io/docs/polyfills/intl-numberformat)) (judgment).
  - **Time zones.** FormatJS's `DateTimeFormat` knows named zones only after a tz-data import, uses UTC as the default zone until `__setDefaultTimeZone` is called, ships IANA tzdb 2026f, and covers DST "until 2100" ([intl-datetimeformat](https://formatjs.github.io/docs/polyfills/intl-datetimeformat)). Measured in 8.0.2: the smaller "golden" set has 247 zones and lacks `Europe/Kyiv`, so load `add-all-tz` (427 zones).
  - **`formatToParts`.** Hermes's Apple backend builds `DateTimeFormat.formatToParts` by splitting the formatted string at each non-alphanumeric character and matching the pieces to the pattern's letters ([source](https://github.com/facebook/hermes/blob/static_h/lib/Platform/Intl/PlatformIntlApple.mm)). Its maintainers disabled it in 2023 as "broken in several aspects" ([#1155](https://github.com/facebook/hermes/pull/1155)), since iOS APIs "are not sufficiently broad on iOS to create a correct implementation" ([#1172](https://github.com/meta/hermes/issues/1172), still open). They restored it in 2025 because "the community started depending on it" ([#1567](https://github.com/facebook/hermes/pull/1567)). `NumberFormat.formatToParts` is compiled out on Apple (`#ifndef __APPLE__` in [Intl.cpp](https://github.com/facebook/hermes/blob/static_h/lib/VM/JSLib/Intl.cpp)).
  - **Temporal.** `temporal-polyfill` captures `Intl.DateTimeFormat` when it loads, and computes each zone offset with `formatToParts` on an `en-u-hc-h23` formatter with era and ISO calendar ([intlFormatUtils.ts](https://github.com/fullcalendar/temporal-polyfill/blob/main/polyfill/src/internal/intlFormatUtils.ts), [timeZoneId.ts](https://github.com/fullcalendar/temporal-polyfill/blob/main/polyfill/src/internal/timeZoneId.ts), [timeZone.ts](https://github.com/fullcalendar/temporal-polyfill/blob/main/polyfill/src/internal/timeZone.ts)). It also takes the device zone from `new RawDateTimeFormat().resolvedOptions().timeZone` ([current.ts](https://github.com/fullcalendar/temporal-polyfill/blob/main/polyfill/src/internal/current.ts)), and FormatJS's default zone is UTC. So import it after FormatJS's `DateTimeFormat` and `add-all-tz`, and after `__setDefaultTimeZone` with the zone that native code reports; otherwise "now" is in UTC (judgment). Spike L4 checks the result against native Temporal.
  - **Text.** Hermes has no `Intl.Segmenter` ([FormatJS guide](https://formatjs.github.io/docs/guides/react-native-hermes)). Grapheme limits need only `unicode-segmenter/grapheme` 0.17.3 (MIT, Unicode 17.0.0), which reports 15.8 KB of Hermes bytecode against 329.5 KB for `@formatjs/intl-segmenter` 12.1.0 (its [README](https://github.com/cometkim/unicode-segmenter)'s own benchmark). `String.prototype.normalize` and case mapping call CoreFoundation on Apple ([PlatformUnicodeCF.cpp](https://github.com/facebook/hermes/blob/static_h/lib/Platform/Unicode/PlatformUnicodeCF.cpp)), so `searchKey()` needs no polyfill.
  - **Collation.** `Intl.Collator` stays native. Hermes maps `numeric` to `NSNumericSearch` and `sensitivity` to Foundation compare options, then calls `-[NSString compare:options:range:locale:]` ([source](https://github.com/facebook/hermes/blob/static_h/lib/Platform/Intl/PlatformIntlApple.mm)), which is not ICU's collator, so §6's French order must be re-checked there (spike L2). FormatJS's `@formatjs/intl-collator` is at 0.3.1, first published 2026-05-14 ([npm](https://www.npmjs.com/package/@formatjs/intl-collator)).
  - **Week data.** With no `Intl.Locale` there is no `getWeekInfo()`. The FormatJS `Locale` polyfill implements it (present in the 5.4.2 bundle), but the resolver takes a region's default first day from a pinned CLDR table on every platform (§3.2).
  - **Size (measured, unminified published files).** The seven polyfill bundles above, `@formatjs/intl-segmenter` and `temporal-polyfill` total 1.24 MB; the en and fr locale data plus `add-all-tz` (1.37 MB alone) total 2.45 MB. That is 3.7 MB in all, or 0.62 MB gzipped. Each bundle repeats shared helpers, so a Metro build is smaller; the start-up cost is spike L2's to measure.
  - FormatJS also ships a Rust-backed "Hermes Intl SDK" with twelve Intl APIs and Apple archives. Its `DateTimeFormat` starts with UTC only, and its documented example is an Android app ([guide](https://formatjs.github.io/docs/guides/hermes-intl)). It is a spike item, not a pick.
- **A web app in native shells.** The WebView runs the system WebKit, so the Safari rules for that OS version apply (judgment).
- **Either way**, the watch app and the extensions stay Swift, so the Apple output of the generator is needed.

**Generator design (B, judgment).**
- **Input.** `en.json` holds `{key: {message, description, maxLength?, platforms?}}` and `fr.json` holds `{key: message}` or `{key: {message, state: "needs_review"}}`. Keys are sorted, with one key per line.
- **Checks.** It parses messages with `@formatjs/icu-messageformat-parser` 3.5.22 and enforces the §7 subset. It runs `formatjs verify --missing-keys --structural-equality` on the JSON, and the same command in Apple mode on the generated catalogs: `formatjs verify "…/*.xcstrings" --message-syntax apple-printf --structural-equality --missing-keys` ([CLI](https://formatjs.github.io/docs/tooling/cli)). It also runs French typography lint, length budgets and unused-key detection.
- **Apple output.**
  - `Packages/Strings`, used by the watch app, the widgets and the NSE: a generated `Localizable.xcstrings` (manual keys, positional `%1$@`/`%2$lld`, at most one plural variation per key) and public Swift accessors returning `LocalizedStringResource`.
  - ICU `=0` becomes Apple's `zero` plural variation in languages without a CLDR `zero` category, such as en and fr (measured, §2.1). Elsewhere, as in Latvian, it becomes a separate key such as `tx.count#zero`. `select` branches become separate keys such as `partner.added#feminine`, and the accessor dispatches between them.
  - Strings that iOS reads from a bundle go to the target that owns the bundle. The push-fallback keys go into the app target's own `Localizable` table (§6). An `InfoPlist.xcstrings` for `NSFaceIDUsageDescription` and the like goes into each target that owns an Info.plist; for an Expo app target, the generator emits the per-language JSON files of Expo's `locales` config instead ([Expo](https://docs.expo.dev/guides/localization/)).
- **Shared UI output (iPhone, Mac, web).** `formatjs compile --ast` JSON per locale, plus a typed module (`m.budget.safeToSpend({ amount })`). `compile` runs on native Rust bindings with "no JavaScript compiler fallback". CI images must therefore keep optional dependencies enabled, which installs the matching `@formatjs/cli-native-*` package (for example `linux-x64` or `linux-x64-musl`).
- **Server output.** TypeScript reuses the web output. For a Swift server, it emits Swift functions with built-in en/fr plural rules (spike L1).

### 2.4 Writing rules for messages

- **Plural rules.** In CLDR 49, English `one` = `i = 1 and v = 0`. French (shared with Portuguese since CLDR 49) has `one` = `i = 0..1` and `many` = exact millions ([plurals.xml](https://github.com/unicode-org/cldr/blob/release-49/common/supplemental/plurals.xml)). Measured with `Intl.PluralRules`: French 0 → one, 1.5 → one, 1,000,000 → many; English 0 → other. French therefore says "0 transaction" where English says "0 transactions". Write `=0` for empty states in both. A missing French `many` falls back to `other`, which is acceptable (judgment).
- **Gender.** French copy addresses the user. Write neutral sentences ("Votre budget est à jour", not "Vous êtes prêt"), and use `select` only on an explicit stored enum, never on a value guessed from a name (judgment). Apple's term-of-address setting exists on the device, but only Swift code can use it; the shared UI would need a profile field (judgment).
- **Text expansion.** IBM's figures for English into European languages, via [W3C](https://www.w3.org/International/articles/article-text-size):

  | English length | Expected size |
  |---|---|
  | ≤ 10 characters | 200–300% |
  | 11–20 | 180–200% |
  | 21–30 | 160–180% |
  | 31–50 | 140–160% |
  | 51–70 | 151–170% |
  | > 70 | 130% |

  Watch, widget and button strings carry `maxLength` and a `.short` key. Design-system components are documented with English, French and pseudo-long content (judgment).
- **French typography.** French puts a no-break space before `; : ! ?` and inside « » (convention, not verified against a primary standard), so lint for U+202F/U+00A0 there. Digit grouping has used U+202F since [CLDR 34](https://cldr.unicode.org/downloads/cldr-34), and only formatters produce numbers.
- **MessageFormat 2.** The spec became Stable in [CLDR 47](https://cldr.unicode.org/downloads/cldr-47), and `:currency`/`:percent` became Stable in [CLDR 49](https://cldr.unicode.org/downloads/cldr-49) (2026-10-22). ICU 79 updated its C++ and Java MF2 code to CLDR 49, but "some of the API remains in technology preview" ([ICU 79](https://unicode-org.github.io/icu/download/79.html)), and `Intl.MessageFormat` is at TC39 Stage 1 ([proposals](https://github.com/tc39/proposals/blob/main/ecma402/README.md)). Don't adopt it yet. The §7 subset maps one-to-one onto MF2 `.match` (judgment).

### 2.6 Agent workflow with review

1. **Write both languages.** The agent adds or changes keys in `en.json`, with a description and a `maxLength` for constrained UI. It writes `fr.json` in the same commit, following `l10n/glossary.yaml` and `l10n/style/fr.md` (vouvoiement; "reste à vivre", "épargne de précaution", from [budgeting-products.md](budgeting-products.md)). Then it runs `mise run l10n` to generate and check (`mise` is the entry point in [factory-ci-quality.md](factory-ci-quality.md)).
2. **CI blocks** on invalid ICU, subset violations, placeholder or plural mismatches, a missing French message, typography, length budgets, and literal UI strings (SwiftLint custom rule; `formatjs/no-literal-string-in-jsx`).
3. **The owner reviews French.** CI posts an EN/FR side-by-side table of the changed messages, and the owner approves the French. The owner is the only native reviewer, and an agent never self-approves copy.
4. **Snapshots.** CI runs French and pseudo-locale snapshot runs for changed screens (FormatJS `en-XA` for the shared UI, Xcode's double-length pseudolanguage for the watch app and widgets).
5. **More languages later.** An agent drafts `xx.json` marked `needs_review`; a native friend reviews it in the PR or in Tolgee; the release gate refuses `needs_review` in shipped locales. Xcode 27's agent translation isn't used on generated catalogs, because the next generation would overwrite it (judgment).

## 3. Regional formatting

### 3.1 Platform APIs (Nov 2026)

- **Apple (Swift targets)**
  - Use `Date.FormatStyle`, `Decimal.FormatStyle.Currency`, `ListFormatStyle` and `Duration` styles. Apple: "don't use Float or Double to represent currency… Use Decimal" ([Apple](https://developer.apple.com/documentation/xcode/preparing-dates-numbers-with-formatters)).
  - `Locale.Components.region` overrides "region-related preferences, such as measuring system, calendar, and first day of the week" ([doc](https://developer.apple.com/documentation/foundation/locale/components/region)). `hourCycle` overrides the hour cycle ([doc](https://developer.apple.com/documentation/foundation/locale/components/hourcycle)), and `firstDayOfWeek` is available too ([doc](https://developer.apple.com/documentation/foundation/locale/firstdayofweek)).
  - Measured: components {fr, FR, region DE, h23, Monday} serialize to `fr_FR@fw=mon;hours=h23;rg=dezzzz`, which is `fr-FR-u-fw-mon-hc-h23-rg-dezzzz` in BCP 47, and the identifier parses back.
- **JavaScript (shared UI and web)**
  - Measured: `hour12` overrides `hourCycle`. `-u-fw-` and `-u-rg-` change `getWeekInfo()`, but `rg` doesn't change number or date output. `pt-PT` starts weeks on Sunday on every engine.
- **Hermes (if the shared UI is React Native)**
  - Its Apple `Intl` has only `Collator`, `NumberFormat` and `DateTimeFormat` (§2.2). `DateTimeFormat` reads `hourCycle` and splits strings for `formatToParts`, and `NumberFormat` reads no `roundingMode` ([source](https://github.com/facebook/hermes/blob/static_h/lib/Platform/Intl/PlatformIntlApple.mm)). Its feature list puts Temporal under "Currently absent" ([Features.md](https://github.com/facebook/hermes/blob/static_h/doc/Features.md)). Not measured.

### 3.2 System settings vs app overrides

- **Apple settings.** The OS lets people set Region, Date Format, Number Format, First Day of Week and 24-hour time ([iPad guide](https://support.apple.com/guide/ipad/ipad0cc6a80b/ipados)), and choose a language per app. I found no per-app *region*.
- **Browsers.** Browsers expose the browser language, not OS regional overrides. Edge's default "Limited" mode passes the OS region to `Intl` only when its language matches the browser's, "similar to current Firefox behavior", for fingerprinting reasons, and never to `navigator.language` or `navigator.languages` ([Microsoft](https://learn.microsoft.com/microsoft-edge/web-platform/os-regional-settings)). A Mac with English as the language and France as the region (`en_US@rg=frzzzz`) is exactly the case the web can't detect: Safari's WebKit prints `-€1,234.50` there while the Mac shows `-1 234,50 €` (measured, below). A JavaScript UI inside a native app can read these settings through native code instead. Expo's `expo-localization` exposes `regionCode`, separators, `uses24hourClock` and `firstWeekday` on iOS and Android but lists no macOS, and on iOS "the results will remain the same while the app is running". On the web its `regionCode` "is parsed from locale" ([Expo](https://docs.expo.dev/versions/latest/sdk/localization/)).
- **Resolver (judgment, measured).** One function, implemented in Swift and TypeScript and tested against the same golden vectors, maps the stored preference to:
  - **Swift targets (watch app, widgets, NSE):** `Locale(identifier: "<languageTag>-u-rg-<region>zzzz[-hc-…][-fw-…]")`, set as `\.locale` at the root of each.
  - **JavaScript (shared UI on iPhone, Mac and web), words:** `textLocale = <languageTag>` (+ `-u-hc-`). It formats month and weekday names, relative time, lists and plurals.
  - **JavaScript, numbers:** `numberLocale` = `<language>-<REGION>` when that pair is on the allowlist of real CLDR regional locales (fr-BE, fr-CH, de-AT, en-IE…), otherwise the region's primary locale (FR→fr-FR, DE→de-DE, BE→nl-BE…), plus `-u-hc-`. It formats numbers, currency, numeric dates and times.
  - **Week start and hour cycle:** from the preference, else the OS on Apple, else the region's row in a pinned CLDR 49 table generated with the digit table. Its `weekData` starts weeks on Monday in every European region except PT, MT and IS (Sunday), and its `timeData` prefers 24-hour time everywhere in Europe except GR, CY and AL (measured from [supplementalData.xml](https://github.com/unicode-org/cldr/blob/release-49/common/supplemental/supplementalData.xml)). Engines and libraries carry their own copies, so the resolver always passes both values explicitly (judgment).
  - **Inputs** take the same locales plus that explicit hour cycle and first day (§3.3).
  - **Design-system components** (`MoneyAmount`, `DateText`, `TimeText` in [design-system.md](design-system.md), and the inputs of §3.3) call the resolver and never construct locales themselves.

**Auto detection.**
- **Apple (Swift targets, and the shared UI through native code):** the language comes from the bundle's resolved localization (not the device language, so a German iPhone running the English UI formats as `en@rg=dezzzz` rather than mixing German month names into English text). Region, hour cycle and first day come from `Locale.autoupdatingCurrent`, re-read on `currentLocaleDidChangeNotification`. Ranked preferences come from `Locale.preferredLocales` (iOS, watchOS and macOS 26+), which honours per-app overrides (§2.1).
- **Web, the Mac's Dock web app included:** the browser yields only a language.
  - Measured in Safari 26.6.2's WebKit on the Mac of §1: `navigator.languages` is `["en-US"]`, and `Intl` defaults print `-€1,234.50`, `11/7/2026` and `7:05 PM`, with weeks starting on Sunday. Only the zone, `Europe/Paris`, matches the Mac. WebKit takes the OS language list and minimizes it "to reduce fingerprinting" ([LanguageCF.cpp](https://github.com/WebKit/WebKit/blob/main/Source/WTF/wtf/cf/LanguageCF.cpp)); the same `NSLocale` call turned this Mac's `en-US, en-FR, fr-FR` into `en-US, en` (measured). JavaScriptCore's default locale is that first language ([IntlObject.cpp](https://github.com/WebKit/WebKit/blob/main/Source/JavaScriptCore/runtime/IntlObject.cpp)), with no region or hour-cycle override.
  - So on the web "auto" resolves in this order (judgment). (1) The region, hour cycle and first day that the user's Apple apps last reported on sync (§6), most recent device first, shown in settings as "From your iPhone: France · 24-hour · Monday". (2) Otherwise a one-time "Formats" step at the web app's first run, pre-filled from the browser's zone (`Europe/Paris` → FR through [zone.tab](https://data.iana.org/time-zones/tzdb/zone.tab)), the household's base currency and the language's region, and saved as explicit values. The language itself comes from `languageTag`, else `navigator.languages`.
- **iPad app on the Mac:** it runs the iOS binary, so native code should read the Mac's region, 24-hour and first-day settings as on the iPhone (inference). Apple's guide to iOS apps on the Mac says nothing about language or region, so the per-app language there is spike L3.

An explicit region, hour cycle or first day of the week wins on every device. The language doesn't. Apple says not to set the app language in code, and the Apple UI language is the bundle's resolved localization (L1), so a language chosen on the web can't reach the iPhone, Mac or watch. `languageTag` therefore drives only the web app and email. Each Apple app reports its per-app language as the device's `ui_language`, plus the region, hour cycle and first day that the web's "auto" borrows (§6). Number-separator presets (iOS "Number Format") are deferred (open question). **M-H**

### 3.3 Date, time and amount input

Formatting through the resolver isn't enough: a picker left on its defaults follows the device or the browser, so a 24-hour profile can still get a 12-hour picker.

- **Browser controls (measured on the Mac of §1).** `<input type="time" value="19:05">` and `<input type="date">` render as `07:05 PM` and `11/07/2026` in Safari 26.6.2's WebKit, even inside `lang="fr-FR"` or `lang="en-GB"`. Headless Chrome 157 renders `19:05` and `07/11/2026` and ignores `lang` too (`de-DE` still gives `07/11/2026`): Blink switches to `NSLocale.currentLocale` whenever the browser's language matches the Mac's ([locale_mac.mm](https://github.com/chromium/chromium/blob/main/third_party/blink/renderer/platform/text/locale_mac.mm)). MDN promises only a display "based on the locale of the user's browser" ([date](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/input/date), [time](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/input/time)). So one page shows two formats in two browsers on one Mac, and neither follows the profile.
- **iOS pickers.** UIDatePicker's `locale` defaults to the device's current locale, and its `calendar` to the one "configured in Settings" ([locale](https://developer.apple.com/documentation/uikit/uidatepicker/locale), [calendar](https://developer.apple.com/documentation/uikit/uidatepicker/calendar)).
  - Expo UI's SwiftUI `DatePicker` (SDK 58) is iOS-only. It takes the locale and the zone through `environment('locale', …)` and `environment('timeZone', …)`, and the modifier's only keys are `colorScheme`, `editMode`, `locale` and `timeZone`, with no `calendar` ([DatePicker](https://docs.expo.dev/versions/v58.0.0/sdk/ui/swift-ui/datepicker/), [modifiers](https://docs.expo.dev/versions/v58.0.0/sdk/ui/swift-ui/modifiers/)). So the first weekday must ride in the locale identifier.
  - Measured on macOS 26.6.2: a SwiftUI `DatePicker` whose `\.locale` is `en_US@hours=h23;fw=mon` shows `19:05` and a calendar starting on Monday, without `\.calendar`; plain `en_US` shows `7:05 PM` and Sunday. macOS draws it with AppKit, so iOS's UIKit picker is spike L2.
  - `@react-native-community/datetimepicker` 9.3.0 targets iOS, Android and Windows, not the web. Its `is24Hour` and `firstDayOfWeek` are Android- and Windows-only, and its README discourages the iOS `locale` prop "due to not working reliably in all picker modes" ([README](https://github.com/react-native-datetimepicker/datetimepicker)).
- **Pick for the Expo stack (judgment).**

## 4. Time

| Concept | JSON | Swift | TypeScript | PostgreSQL |
|---|---|---|---|---|
| Instant (created, synced, sent) | RFC 3339 UTC `2026-11-07T18:05:00.000Z` | `Date`, "a specific point in time, independent of any calendar or time zone" ([doc](https://developer.apple.com/documentation/foundation/date)) | `Temporal.Instant` | `timestamptz`, "stored internally in UTC" ([docs](https://www.postgresql.org/docs/18/datatype-datetime.html)) |
| Civil date (booking, value, transaction, due date, period bounds) | `2026-11-07` | `CivilDate` value type in `Domain` | `Temporal.PlainDate` | `date` |
| Budget month | `2026-11` | `YearMonth` | `Temporal.PlainYearMonth` | `date` (1st of month) |
| Local time of day (reminder 20:00) | `20:00` | `CivilTime` | `Temporal.PlainTime` | `time` (PostgreSQL advises against `time with time zone`) |
| Zone | IANA ID `Europe/Paris` | `TimeZone(identifier:)` | zone ID string | `text`, validated |

- **Bank dates have no time and no zone.**
  - Enable Banking, the provider recommended in [bank-aggregation.md](bank-aggregation.md), types `booking_date`, `value_date` and `transaction_date` as `string(date)`. For a card payment, `transaction_date` is the "date of the transaction". All three are optional (`Required: false`), so the budget date needs a fallback chain (T5) ([API ref](https://enablebanking.com/docs/api/reference/)).
  - Enable Banking's transactions endpoint takes `date_from` and `date_to` as dates for which "UTC timezone is assumed" (same reference). So compute sync windows as UTC dates, never as household-zone dates. The `date_from = last_booked_date − 7 d` overlap in [bank-aggregation.md](bank-aggregation.md) already covers the few hours between the household zone and UTC around midnight (judgment).
  - GoCardless also uses ISODate `bookingDate`/`valueDate` plus optional `…DateTime` fields ([docs](https://docs.gocardless.com/docs/bank-account-data/output-transaction-details)).
  - Never pass a civil date through `Date`/`Instant`: stored as midnight UTC, it displays as the previous day in the Azores (UTC−1); stored as midnight in Paris, it is the previous day in UTC.
- **The household zone is shared data.** "Today", payday, month and week boundaries, limit pacing and due dates are evaluated in it. Periods are calendar months, as the owner confirmed ([PRODUCT.md](../../PRODUCT.md), and *Period* in [GLOSSARY.md](../../GLOSSARY.md)): half-open civil ranges `[first of the month, first of the next month)` in the household zone. Only the safe-to-spend horizon is undecided (month end or next payday), so a payday rule matters only for that horizon and for income forecasts.
  - Measured: the instant 2026-11-07T23:30Z is 8 November in Paris but 7 November in London.
  - Measured: 2027-03-28 lasts 23 hours in Paris.
  - Month-end clamping must be explicit: Temporal gives 2026-01-31 + 1 month = 2026-02-28 (measured).
  - France isn't one zone: overseas departments use the euro and French banks in `Indian/Reunion`, `America/Martinique` and others ([zone.tab](https://data.iana.org/time-zones/tzdb/zone.tab), [ISO 4217](https://www.six-group.com/dam/download/financial-information/data-center/iso-currrency/lists/list-one.xml)). Take the zone from the device, never from the country.
- **DST.** EU clocks change at 01:00 GMT on the last Sunday of March and October ([Directive 2000/84/EC](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX:32000L0084), Arts. 2–3). Abolition is stalled: the Council never agreed, and a Commission study is due by end-2026 ([Finnish government, 2026-03-25](https://valtioneuvosto.fi/en/-/1410829/clocks-go-forward-as-summer-time-begins-on-sunday-29-march)). Keep the rules data-driven.
- **Gap and overlap policy differs (measured and documented).**
  - Spring-forward gap: Apple `Calendar.date(from:)` and Temporal `compatible` turn Paris 2027-03-28 02:30 into 03:30+02:00. PostgreSQL treats an invalid time "as if it were standard time" ([docs](https://www.postgresql.org/docs/18/datetime-invalid-input.html)), which also gives 03:30.
  - Fall-back overlap: Apple and Temporal pick the earlier 02:30+02:00, while PostgreSQL picks standard time, the *later* one.
  - So app code does every local-to-instant conversion with `compatible`, and SQL never does.
- **Scheduling alerts.**
  - Store the rule, the local time and the zone. Compute the next instant, and recompute after each fire and whenever the zone or tzdata changes; never repeat every 24 hours.
  - Daily reminders that don't depend on server data can be local `UNCalendarNotificationTrigger`s built from date components ([doc](https://developer.apple.com/documentation/usernotifications/uncalendarnotificationtrigger)). Whether they follow the device across zones is not verified; see spike L4.
  - Quiet hours use the device's current zone, which each device reports on sync.
- **Travel.** Budget math stays in the household zone. A user's own reminders follow the device zone unless pinned. Show a hint when the device zone differs from the household zone (judgment).
- **tz database.** There were six releases in 2026, the latest being 2026f on 2026-10-27 (Cuba changed its rules days ahead of a transition); 2026a fixed Moldova's EU transition times ([NEWS](https://data.iana.org/time-zones/tzdb/NEWS)). Measured: macOS 26.6.2 already had 2026f, while Node 24.22 and 26.13 had 2026e. Keep the server's OS tzdata and PostgreSQL minor releases current. On Hermes, zone rules come from FormatJS's bundled data (2026f in 8.0.2), not from iOS, so after a rule change the iPhone's shared UI and its own watch app can disagree until the next app release. Ship FormatJS updates with tzdb releases (judgment).
- **Zone IDs.** Treat them as opaque strings and compare them through a canonicalization table. Chrome 157 and Node 24.22 and 26.13 turn `Europe/Kyiv` into `Europe/Kiev` and `CET` into `Europe/Brussels`, while Apple and the Safari 26.6.2 engine keep both (measured). Safari 27 changed its time-zone ID handling (§1), so re-measure Safari 27.2.

### 5.3 Formatting, rounding, input

- **Symbol position and separators follow the locale (measured).**
  - `-1 234,50 €` (fr), `-1.234,50 €` (de), `€ -1.234,50` (nl), `-€ 1.234,50` (de-AT), `-1234,50 €` (it, es, pt, pl: no grouping below 10,000), `EUR-1'234.50` (de-CH).
  - sv, fi and hr use U+2212 for the minus sign. In French, USD prints as `12,50 $US`.
  - Never hardcode a symbol; use `currencyDisplay: "code"` in mixed-currency tables.
- **Rounding.** Apple's FormatStyle rounds half-even by default (2.5 → 2, 0.125 → 0.12), while Intl rounds half-expand (2.5 → 3) (measured). Formatters receive exact minor-unit values, plus an explicit rounding rule for any display rounding (compact amounts): `.rounded(rule: .toNearestOrAwayFromZero)` and `roundingMode: "halfExpand"`.
- **Splits and percentages.** Compute in minor units, and allocate by largest remainder so the parts sum to the total (judgment).
- **Input.** Typed amounts follow §3.3: `,` or `.` as the decimal separator, no grouping, an exact parse. CSV imports parse each bank's known format (`;` separators, decimal comma, `dd/mm/yyyy`, per [bank-aggregation.md](bank-aggregation.md)) instead of guessing from the locale.

### 5.4 Multi-currency and FX

- **ECB reference rates.** They cover 29 currencies, about 16:00 CET on TARGET working days, and "are published for information purposes only". Per the ECB, "using the rates for transaction purposes is strongly discouraged". The RUB rate has been suspended since 2022-03-01, and there is no BGN rate any more ([ECB](https://www.ecb.europa.eu/stats/policy_and_exchange_rates/euro_reference_exchange_rates/html/index.en.html)). RSD, ALL, MKD, BAM, MDL, UAH, GEL, AMD, AZN, BYN and RUB are not covered.
- **Rounding precedent.** The euro changeover rules used six-significant-figure rates, "not rounded or truncated", no inverse rates, and results rounded to the nearest cent with exact halves rounded up ([Regulation 1103/97](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX:31997R1103), Arts. 4–5). Use the same rules for the app's own conversions (judgment), except the six figures. The ECB publishes fewer digits for most currencies: on 2026-11-06, CHF 0.9143, USD 1.1165 and JPY 176.77, between 4 and 7 significant digits across its 29 currencies ([daily XML](https://www.ecb.europa.eu/stats/eurofxref/eurofxref-daily.xml)). So store a published or bank-applied rate verbatim, and keep at least six significant figures only for rates the app derives, such as a cross rate through the euro (judgment).
- **Design (M, judgment).**
  - Each household has one base currency. Categories and envelopes hold only the base currency; YNAB likewise has "one currency per plan" ([budgeting-products.md](budgeting-products.md)).
  - Card spending abroad from a euro account is booked in euros. Keep `exchange_rate.instructed_amount` for display only.
  - A foreign-currency account (Revolut, Wise) converts each transaction at the bank's applied rate when known, or else at the latest ECB rate on or before the booking date. Store the original amount, the converted amount, the rate (a decimal string, exactly as published or applied), the source and the rate date, and never recompute them.
  - A balance shows "≈" in the base currency at the latest rate.
  - A non-ECB currency needs a manual rate in v1.

## 6. Backend

| Owner | Field | Format |
|---|---|---|
| User (synced) | `language_tag` (web app; default for email), `region`, `hour_cycle`, `first_day_of_week`, `email_language` | BCP 47 / ISO 3166-1 alpha-2 (+ `XK`) / `h12`·`h23`·null / ISO weekday·null / BCP 47 |
| Device | `ui_language` (resolved bundle language on Apple, which `language_tag` never overrides), `locale_identifier`, `hour_cycle`, `first_day_of_week` (the OS values that the web's "auto" borrows, §3.2), `time_zone`, `tzdata_version`, `app_version` | Reported on every sync |
| Household | `time_zone`, `base_currency`, `week_start`, payday rule (for income forecasts, and for the safe-to-spend horizon if it runs to payday) | IANA / ISO 4217 / ISO weekday / rule object |
| Text | Category names, notes, payees | As typed, NFC-normalized at the API; limits counted in grapheme clusters (Swift `count`, `Intl.Segmenter`, `unicode-segmenter` on Hermes), with the API's count authoritative |
| Built-in categories | `system_key` (e.g. `groceries`), rendered in each viewer's language; a rename stores a custom name that is never translated | So a mixed-language household sees its own language |

- **Push.**
  - The payload carries an event type and raw values (minor units, currency, civil dates, IDs), encrypted as [apple-client-stack.md](apple-client-stack.md) proposes. The notification service extension renders the text with the device's catalog and resolver.
  - The visible fallback shown if decryption fails is a `loc-key` with no amounts, so the server doesn't need the language (judgment). APNs reads that key from "the Localizable.strings file of your app bundle" (§2.1), so the generator writes the fallback keys into the app target's own catalog. Left only in `Packages/Strings`, they would sit in the package's `Bundle.module`, and the alert would show the raw key (inference).
  - Web push is rendered in the service worker with the web catalog.
  - Language is per device: a Mac in English and an iPhone in French are both normal.
- **Email.** Render server-side in `email_language`, from the same catalog and resolver, with dates in the household zone. TypeScript reuses FormatJS. Swift uses generated functions; swift-foundation runs the same `Locale`/FormatStyle code on Linux with ICU 76.1, the version on swift-foundation-icu's main and 6.4 release branches ([swift-foundation](https://github.com/swiftlang/swift-foundation), [uvernum.h](https://github.com/swiftlang/swift-foundation-icu/blob/main/icuSources/include/_foundation_unicode/uvernum.h)). ICU 76 carries CLDR 46 ([ICU 76](https://unicode-org.github.io/icu/download/76.html)), older than the CLDR 48 in Node's bundled ICU 78.3. CLDR 46 still gave HUF 2 display digits where CLDR 48 and 49 give 0 ([CLDR 46 supplementalData](https://github.com/unicode-org/cldr/blob/release-46/common/supplemental/supplementalData.xml)), so a Linux Swift server would drift from the devices without the pinned digit table (inference, not run on Linux). Emails therefore take digits from that table (L4) and get their own golden tests.
- **Search (M).**
  - **One spec, everywhere.** `searchKey()`: NFKD → drop marks (Mn) → full case folding → map ß→ss, æ→ae, œ→oe, ø→o, ł→l, đ→d, ı→i. Implement it in Swift and TypeScript against shared vectors. Store the key in each client's SQLite and on the server.
  - **Why the explicit mapping.** Measured: Swift's `folding(.caseInsensitive, .diacriticInsensitive)` and Python's NFKD + casefold both leave ł, ø, đ, æ and œ unchanged. JavaScript `toLowerCase()` keeps "straße", while Swift folds it to "strasse".
  - **Device full-text search.** Use the FTS5 `unicode61` tokenizer with `remove_diacritics 2` ([SQLite](https://www.sqlite.org/fts5.html)) where the client's SQLite build includes FTS5; [cross-platform-ui-stack.md](cross-platform-ui-stack.md) notes that `expo-sqlite` has "no FTS by default". Otherwise use `LIKE` on `search_key`.
  - **Server.** PostgreSQL 18 allows `LIKE` with nondeterministic collations and adds `casefold()` ([release notes](https://www.postgresql.org/docs/18/release-18.html)). For accent- and case-insensitive comparison, its docs use `und-u-ks-level1` (`ignore_accent_case`). Their `und-u-ks-level1-kc-true` example (`ignore_accents`) stays case-sensitive: with `kc` true at level 1 the collation "will ignore accents but take case into account" ([collations](https://www.postgresql.org/docs/18/collation.html)). `ILIKE`, `SIMILAR TO` and POSIX regular expressions don't support nondeterministic collations ([pattern matching](https://www.postgresql.org/docs/18/functions-matching.html)). [`unaccent`](https://www.postgresql.org/docs/18/unaccent.html) is the alternative. Enforce case- and accent-insensitive name uniqueness with a unique index on `search_key`.
- **Sorting.** Sort on the client with the UI language's collator (`localizedStandardCompare`, `Intl.Collator(lang, {numeric: true})`). Measured French order: cote, coté, côte, côté; `fr-CA` sorts accents backwards. On Hermes, `Intl.Collator` is Foundation's `NSString` comparison (§2.2), so check this order there too (spike L2). Server ordering is only for paging.

## 7. Data and formatting contract

**Strings**
- **S1.** No user-visible literal in UI code: text comes from `l10n/messages` through generated accessors, and lint enforces it.
- **S2.** Keys are stable, semantic and dotted (`budget.safeToSpend.title`). A new meaning gets a new key.
- **S3.** Every source message has a description (where it appears, what each argument is). Constrained UI also has `maxLength` in graphemes and a `.short` key.
- **S4.** The ICU subset allows:
  - literal text;
  - `{arg}` for a pre-formatted string;
  - `{count, plural, =0 {…} one {…} other {…}}` with `#`;
  - `{enum, select, … other {…}}`.

  Each message has at most one plural and one select. Not allowed: `number`, `date` or `time` arguments, `offset`, `selectordinal`, markup.
- **S5.** No sentence is built by concatenation: format the values first, then pass them as arguments.
- **S6.** English is the source and French is required in the same PR. At runtime, fr falls back to en.
- **S7.** French follows the style guide: vous, the glossary, no-break spaces, gender-neutral copy. `select` applies only to explicit enums.

**Locale**
- **L1.** The stored preference is `{languageTag, region, hourCycle, firstDayOfWeek}`, each "auto" or explicit. An explicit region, hour cycle or first day wins on every device. "Auto" means the OS on Apple; on the web it means the values the user's Apple apps last reported, else a first-run choice saved as explicit (§3.2). `languageTag` drives only the web app and email. On Apple, the UI language, shared UI included, is the bundle's resolved localization, set in the OS per-app setting and reported per device.
- **L2.** Every platform formats and takes input through the resolver (§3.2, §3.3). No formatter or picker reads the raw system or browser locale, pickers always get the hour cycle and first day explicitly, and the web never uses `<input type=date|time>`. Extensions read the resolved preference from the app group.
- **L3.** Dates and times use named field sets from the contract (`dateNumeric {y,M,d}`, `dateMedium {y,MMM,d}`, `monthYear {MMMM,y}`, `weekdayDay {EEEE,d}`, `time {h|H,mm}`), never preset styles.
- **L4.** Money formatting always passes the currency code, min = max fraction digits from the pinned CLDR table, and an explicit rounding rule.
- **L5.** Only allowlisted locales are used. When an engine lacks a locale (Chrome) or an API (Hermes), load FormatJS polyfills and their locale data; never fall back silently to en-US. On Hermes, load `add-all-tz` and set the default zone before `temporal-polyfill` loads, and count graphemes with `unicode-segmenter` (§2.2).
- **L6.** Relative dates ("hier") come from civil-date differences in the household zone, then go through RelativeTimeFormat or the equivalent Apple style.
- **L7.** Cross-platform golden tests map U+00A0, U+202F and U+2009 to U+0020 and U+2212 to `-`. Per-platform snapshots keep the exact characters.

**Time**
- **T1.** Instants are UTC (RFC 3339 `Z`, `timestamptz`). Civil dates are `YYYY-MM-DD` (`date`) and never pass through an instant.
- **T2.** Zones are IANA IDs, compared after canonicalization. No abbreviations, no fixed offsets.
- **T3.** Household computations ("today", periods, pacing, due dates) use the household zone. User reminders and quiet hours use the device zone.
- **T4.** Local times become instants only in app code, with the `compatible` policy. Schedules are recomputed and never repeat every 24 hours.
- **T5.** Keep all three bank dates; any of them may be missing. The budget date is the first present of `transaction_date`, `booking_date` and `value_date`, else the household-zone date on which the transaction was first seen (order to confirm, see the open questions). A pending entry's date is provisional: when its booked twin replaces it ([bank-aggregation.md](bank-aggregation.md)), the rule runs again.

**Money**
- **M1.** Amounts are an Int64 count of minor units plus an ISO 4217 code, using the pinned ISO table (regenerated from SIX). JSON uses integers; PostgreSQL uses `bigint` + `char(3)`.
- **M2.** Never use Float or Double. Parse providers' decimal strings and typed amounts (§3.3) exactly. A provider's surplus decimal holds the transaction back and flags it; it is never rounded. The amount field rejects one.
- **M3.** FX rates are decimal strings, stored exactly as published or applied. A rate the app derives (a cross rate through the euro) keeps at least 6 significant digits. Results round half-up to the target minor unit and are stored with rate, source and date, frozen.
- **M4.** Each household has one base currency. A split must sum to its total (largest remainder).

**Backend**
- **B1.** Store codes, not formatted text. User text is NFC, with grapheme-counted limits.
- **B2.** Push is rendered on the device, emails on the server, from the same catalog. Push-fallback keys live in the app target's own table. Language is per device for push and per user for email.
- **B3.** `searchKey()` follows one spec with shared vectors. Sorting happens on the client with the UI language collator.

## Recommendation for on-budget

Adopt option B: the canonical ICU catalog in git, the generator, the resolver and the §7 contract before the first screen is built. The shared UI (ADR 0002) consumes the TypeScript output on iPhone, Mac and web; the Swift output serves the watch app, the extensions and the strings iOS reads from bundles. Wire `mise run l10n` into pre-commit and CI from day one. Run spikes L1–L3, and the Hermes part of L4, before the first feature PR. On the Expo stack (React Native), count the FormatJS polyfills, their time-zone data and `temporal-polyfill` in the start-up budget from the first screen: about 3.7 MB of unminified JavaScript for en and fr (measured). Put the date, time and amount inputs of §3.3 into the design system before the first form. Make the web app, the Expo stack's first Mac client, resolve "auto" from the user's Apple devices or from a first-run choice. Trade-offs the owner must accept:

| Decision | Trade-off |
|---|---|
| Generated catalogs instead of Xcode extraction | You own about 500 lines of generator. Apple device variants and inflection are used through extra keys, and only in the Swift targets. Xcode 27 agent translation isn't used on generated files |
| English source, French mandatory in every PR | The owner reviews every French change; no PR merges with French missing |
| Apple follows the OS per-app language; the web has its own picker | One person can run the Mac in English and the iPhone in French; that is a feature, but support questions get harder. The in-app Language row only opens Settings, and iOS may not offer the setting to someone with a single preferred language (L3) |
| One JavaScript formatter for the iPhone, Mac and web screens | In the measured edge cases, the iPhone app can format differently from its own watch app and widgets (Foundation). On Hermes, FormatJS polyfills are mandatory, add start-up cost, and bundle time-zone rules that only an app release updates |
| Profile-driven regional preferences | Rare differences remain (fr-CH currency, pt-PT grouping under an en UI). iOS custom number formats aren't mirrored on the web in v1. The web app can't see the Mac's own settings: it borrows the iPhone's or asks once |
| Controlled date, time and amount inputs | No native `<input type=date\|time>`; every picker gets the profile's locale, hour cycle and first day. Whether iOS's picker honours them is unverified (L2), and the fallback JS picker looks less native |
| Field-based formats only | Less "platform default" look in a few locales; consistent everywhere |
| Household zone defines "today" | While travelling, "today" in the app can differ from the local wall clock |
| Temporal + polyfill | 19.2 kB (min+gzip) wherever Temporal is missing: Safari and iOS before 27.3 (in beta since 2026-11-03), and Hermes, where it also depends on FormatJS's time-zone data (1.37 MB unminified) and is untested (L4) |
| Frozen conversions, one base currency | Past foreign spending doesn't follow today's rate; non-ECB currencies need a manual rate |
| On-device push rendering | Fallback alerts are generic |
| No TMS in v1 | Reviews happen in GitHub, which non-developer translators may dislike |

## Open questions and spikes

**For the owner**
1. Is the source language English (recommended), or is the copy written in French first and English treated as a translation?
2. Tone: vous or tu? Sign-off on glossary terms ("reste à vivre", "épargne de précaution", payday wording).
3. Which date counts for a card payment in the budget, the card date or the booking date? This matters for deferred-debit cards booked at month end. And when a pending payment books in a later month, does it move to that month?
4. For income forecasts, and for safe-to-spend if it runs to the next payday (undecided in PRODUCT.md): payday on a weekend or a holiday, which business-day rule, and which holiday calendars (France only in v1)?
5. Multi-currency in v1: euro-only households, or foreign-currency accounts (Revolut, Wise) from the start?
6. Beyond region, hour cycle and week start, which format overrides matter (separator presets, date order)?
7. Should "today" follow the household zone while travelling (recommended) or the device?
8. The backend language (Swift vs TypeScript) decides how emails are rendered.
9. When will non-developer translators join, and should Tolgee then run in the cloud or self-hosted? The open-source offers also depend on the license, still undecided.
10. Which framework runs the shared UI? ADR 0002 leaves it open, and [cross-platform-ui-stack.md](cross-platform-ui-stack.md) recommends the Expo stack. React Native's Hermes makes the FormatJS polyfills, their time-zone data and `temporal-polyfill` mandatory in the iPhone app (and in the iPad app on the Mac); a web app in native shells uses WebKit's `Intl`.
11. On the web, should formats follow the region, hour cycle and week start that your iPhone reports (recommended), or always be chosen at first run? [PRODUCT.md](../../PRODUCT.md) lists the default language and region rules as undecided.

**Spikes** (≤ 1 day each; pass means agent-built and CLI-tested)
- **L1 Generator round-trip.** EN/FR catalog with `=0`, plural and select → TypeScript used by the shared UI on the iOS Simulator, macOS and the web, and `.xcstrings` compiled by Xcode 27.2 and used from the watch app, a widget and the NSE. Also: Info.plist strings per target, push-fallback keys in the app target, and identical golden strings. The measurement setup in §1 has Command Line Tools only (Swift 6.3.3, no `xcstringstool`), so it needs Xcode 27.2 first.
- **L2 Resolver parity.** Swift and TypeScript resolver; vectors for about 25 (language, region) pairs × numbers, currency, field dates, times, week start. Run them on the iOS 27.2 Simulator (shared UI and widget side by side), macOS 27.2, Safari 27.2, Chrome and Firefox, and on Hermes with FormatJS polyfills if the shared UI is React Native. Re-measure the §1 table there before pinning golden vectors, record the differences, and measure the polyfills' start-up cost with and without `add-all-tz`. On Hermes, also compare its own `formatToParts` with FormatJS's, and check `Intl.Collator` (`numeric`, §6's French order) and `unicode-segmenter` against Swift `count` and Node's `Intl.Segmenter`. Inputs: on iOS 27.2, does Expo UI's `DatePicker` honour `hours=h23` and `fw=mon` in its locale? Under react-native-web, do React Aria's fields keep `hourCycle` and `firstDayOfWeek` with §3.3's split locales? Try FormatJS's Hermes Intl SDK on iOS.
- **L3 Apple locale behaviour in a real bundle.** With only en/fr localizations on a German-language device: is `Locale.current` `en_DE`? Does SwiftUI `\.locale` affect string lookup? How does the shared UI read the resolved localization and `Locale.preferredLocales`? Per-app language relaunch. On iOS 27, does the Language row appear for someone with a single preferred language? Does the setting reach the watch app, as WWDC19 says? On a Mac, does the iPad app read the Mac's region, 24-hour and first-day settings, and where is its per-app language set? Confirm §3.2's WebKit results in Safari 27.2 and in a Dock web app.
- **L4 Time.** Calendar-month periods and both safe-to-spend horizons (month end, next payday), month ends and the DST days 2026-10-25 and 2027-03-28; scheduler vs PostgreSQL; Enable Banking UTC sync windows near midnight in the household zone; travel scenario; whether a local calendar trigger follows a zone change. On Hermes: `temporal-polyfill` offsets and transitions for `Europe/Paris` on both DST days, `Europe/Kyiv`, `Atlantic/Azores` and `Indian/Reunion`, once over Hermes's own `DateTimeFormat` and once over FormatJS with `add-all-tz`, against Node 26's native Temporal; `Temporal.Now.timeZoneId()` with and without `__setDefaultTimeZone`; the start-up cost.
- **L5 Search.** `searchKey()` parity in Swift, TypeScript and PostgreSQL; FTS5 on 50,000 transactions.
- **L6 Push.** NSE renders a localized amount in the device locale, and the `loc-key` fallback, read from the app target's own table, shows when decryption fails.
- **L7 Chrome's missing locales.** Size and correctness of the FormatJS polyfill for `is`, `mt` and `lb`.

## Not verified

- Crowdin and hosted-Weblate prices; Lokalise's annual price. Lokalise lists no free plan besides its free offer to "open source non-profit projects". Whether on-budget qualifies for any open-source offer: the license is undecided, and Crowdin also asks for three months of work and an active community.
- Tolgee says its String Catalog format "supports simple values as well as plural values"; whether its export maps ICU `=0` and `select` is not verified.
- SwiftUI `\.locale` and string lookup, `Locale.current` composition in bundled apps, and per-app region (spike L3).
- Whether the per-app Language row appears on iOS 27 for someone with a single preferred language (WWDC19 says it appears for multilingual users).
- Hermes's `Intl` and the FormatJS polyfills inside a React Native app on iOS and macOS: docs and source only, not measured, and FormatJS's guide disagrees with Hermes on `PluralRules` and `Locale`. The sizes are of the published files, not of a Metro build, and the start-up cost is unknown. Also FormatJS's Hermes Intl SDK on iOS, Hermes's `Intl.Collator` output, and `unicode-segmenter`'s counts against Swift's.
- `temporal-polyfill` on Hermes, over either `DateTimeFormat`, including whether FormatJS's accepts its `calendar: 'iso8601'` formatter there.
- Whether iOS's UIKit picker, under Expo UI's `DatePicker`, honours the `hours` and `fw` locale keywords: measured only with SwiftUI on macOS, where AppKit draws it. Which decimal separator iOS's decimal pad types under a region override.
- The WebKit results come from a `WKWebView` on Safari 26.6.2's framework, not from Safari itself, a Dock web app or Safari 27.2, and Chrome's from headless Chrome.
- How the iPad app on a Mac reads region settings, and where its per-app language is set; Apple's guide is silent.
- The output of Safari 27.2, iOS and macOS 27.2, and the official Node 26.13.0 binary (its ICU 78.3 differs from the measured Homebrew build's 79.1).
- Whether `UNCalendarNotificationTrigger` follows a zone change.
- Runtime `.strings`/`.stringsdict` support in Swift on Linux, and the predicted CLDR 46 drift of a Linux Swift server.
- Chrome's missing locale data was observed in headless Chrome 157 on macOS; Chrome on Android may differ. That system JavaScriptCore equals Safari 26.6.2's engine is an inference.
- French punctuation spacing: based on convention, not a primary standard.
- The release date of Safari and iOS 27.3, whose beta adds Temporal; any euro adoption after 2026 (none scheduled per the ECB report).
- Holiday data sources for business-day rules.
